# ESP32Bridge 文档体系检查

日期：2026-11-07。仓库调查基线：`441a77843ba765cf58dbcdda4d0d55ad2e4f5557`。

## 1. 结论与范围

ESP32Bridge 尚未同步本次已经明确的“前层治理 → Phase → Docs ⇄ 代码”完整体系，仍保留2026-11-05按旧SDD 2.0分流后的职责规定。需要进行本项目的文档纠偏，但不需要推倒已有Docs或照搬SmartCar目录。

主要问题是：Phase设计和映射被降为冻结历史；Docs承载大量未实施目标；部分现行功能的算法、诊断语义和关键参数仍需读源码/历史报告才能了解；现行入口混有过期的工作状态。

本次为只读检查并形成报告，没有修改ESP32Bridge、SmartCar或治理规则，没有运行构建、软件行为测试、烧录或设备复位。既有 `SmartCar/App/system/board_test_config.h` 修改和未跟踪板测方案保持不动。

这是文档结构与代表性实现语义审查，不宣称完成全固件逐函数审计、目标编译或任何实机验收。

## 3. 发现与处理建议

### EDA-01 [P2] 本项目治理仍指向已纠正的旧工作流

证据：

- [AGENTS](../ESP32Bridge/AGENTS.md)第15～16行要求Phase和Docs目标契约先提交，规定Docs独占实现位置/验证方法，不在两层各维护实现表。
- [mission](../ESP32Bridge/specs/mission.md)第22行仍规定Docs维护“当前/目标功能”。
- [Phase02计划](../ESP32Bridge/specs/features/02-scb-protocol/plan.md)第43行明确详细符号、状态、资源、方法不在本计划重复。

影响：后续开发会继续把Phase变成摘要导航，并把未开工设计提前放进现行Docs，与根目录现行规则及用户决定冲突。

建议：同步本项目AGENTS、mission、techstack、code-style职责条款及阶段模板；恢复Phase完整设计/计划/验收责任，明确本组Docs先行与完成时同步规则。保留ESP32的SDK、FreeRTOS、bridge_/scb_命名和阶段审查约束，不引入STM32的R08/AC5/双LCD规则。

### EDA-02 [P2] Phase正文和实施设计仍被降为冻结附件

证据：

- [Phase01需求](../ESP32Bridge/specs/features/01-project-foundation/requirements.md)第7行将详细契约交给Docs；第76～77行起折叠原需求与决定，标为“不作为现行规则”。
- [Phase02需求](../ESP32Bridge/specs/features/02-scb-protocol/requirements.md)第14～15行等FR只指向功能页；第84～85行起才保存原完整需求。
- [Phase03生命周期设计](../ESP32Bridge/specs/features/03-spi-slave/lifecycle-design.md)第3～8行将原设计作为冻结围栏文本；Phase05的[lifecycle-design](../ESP32Bridge/specs/features/05-bridge-lifecycle/lifecycle-design.md)同样处理。
- 本次枚举发现23份Phase Markdown带有冻结包装：6份requirements、6份plan、11份附属设计/决定文件。validation不是同样的整体折叠模式，不能笼统声称18份三件套均被折叠；其中真实历史和决定仍须保留。

影响：读Phase无法直接获得完整开发依据；尚未完成的Phase05详细设计也被放进历史，削弱规约先行。

建议：逐文件恢复阶段正文、设计、任务、映射和验收的主体地位；保留当时基线与后续决定/结果，合并11月5日源码整改增量。原批准冲突不能在恢复中自行裁定。

恢复方式与SmartCar不同：本项目首次导入提交`35e5627`已经包含11月5日文档分流，不能直接把SmartCar的`68cb508`当作ESP32恢复版本。优先从当前文件保存的原文恢复，逐项与来源、历史提交及当前增量对照；不撤销工程导入或已完成的源码格式整改。

### EDA-03 [P2] 未实施桥接目标仍占据现行Docs主体

证据：[桥接页](../ESP32Bridge/Docs/bridge/forwarding-and-lifecycle.md)明确声明F06～F08未完成，但正文继续详细维护COMMAND/RESULT槽位、请求信用、事件缺口、导出状态与锁序等未来设计；F06的3/6/1槽和10240B新增帧数据属于待实现资源方案。

影响：虽然状态标记诚实，Docs仍不是当前代码的完整对应表达；读者需要不断分辨生产路径、目标接口与尚未批准的选项。

建议：将未开工目标、候选资源及未决方案放回Phase05完整设计；Docs保留F06～F08稳定身份，说明当前缺口、已经实现的端口/背压/清理边界和Phase入口。真正进入本组实现时再按已确认设计更新Docs，标本组同步状态。不能以本次文档纠偏启动Phase05/06开发。

### EDA-04 [P2] 部分功能说明还不足以支持Docs到代码的语义互译

证据一：[诊断页](../ESP32Bridge/Docs/system/diagnostics.md)第12行以“不复制第二套完整字段表”为由，将快照定义交回头文件。仅读Docs不能明确下列真实语义：

- `main/net_bridge.h:78`：`received`是HELLO成功及COMMAND/IDLE处理分支数，不是业务交付数；计数点见`net_bridge.c:470/498/539`。
- `main/net_bridge.h:81`：`sent_bytes`含控制和BUSY的正数send字节，不含UDP；写入见`net_bridge.c:644/699`。
- `main/net_bridge.h:92`：`peer_ipv4`是最近记录的对端，连接关闭后可以保留，不代表仍有活动连接。

证据二：[协议页](../ESP32Bridge/Docs/protocol/framing-and-links.md)第14行只概述有界JSON校验，没有展开实际非递归容器状态栈、对象重复键扫描、数值边界检查及精确u32转换机制。实际依据包括`main/json_guard.h:14～25`，`json_guard.c:290/341/497～598/790`等。

证据三：同页第12行把本端协议检查压缩为“检查flags、record_count、LOG_DATA长度和reserved”。`main/protocol.c:225～230/264～289`实际包含遥测记录数1～10、负载长度`24+96*N`、载荷字段/首记录一致性、每记录82～95保留零及LOG_DATA块长1～960、负载长`8+length`等明确条件。公共协议可引用，但本端实际执行的检查矩阵与失败行为仍需说明。

影响：Doc中的功能名称和输入输出大致正确，但读者仍需到源码补出关键实现、计数含义和边界，未达到用户要求的互译深度。

建议：在各自功能主条目展开算法/状态与诊断字段表，逐字段说明触发点、单位、owner、累计/复位、失败和保留。功能页与代码之间必要的同义表达不是应禁止的重复；应避免的是Docs内部出现互相竞争的两套维护位置。

### EDA-05 [P2] 关键参数分散，缺少全局反查与完整来源表

证据：现行网络页说明TCP5000、500ms BUSY、2000ms停滞、任务核/优先级/栈，但没有展示`main/net_bridge.h:21`的backlog=2及第28行的单次poll上限10ms；这些值仍需查源码或历史`Docs/validation/phase-04.md`。当前Docs没有全局参数入口。

建议：建立本项目参数索引，各功能页保存完整明细：真实符号、值/单位、约束、来源、owner、生效/复位时点、是否编译配置、适用状态及源码。至少覆盖SPI/NET任务、DMA/队列容量、引脚/READY、AP/TCP/UDP、重试/等待/停滞、JSON工作区与深度、诊断周期。密码只登记配置键与校验规则，绝不记录实际密码。

明确区分已实现资源与Phase05目标额度，不能把51072B已实现池和10240B拟增数据混成当前内存预算，也不能把静态栈容量写成实测余量。

### EDA-06 [P2] 分类粒度还未区分平台机制、协议算法和整链目标

现有五个职责目录`system/protocol/transport/bridge/guides`总体适合本项目，`Docs/validation/`属于历史证据层，不是第六种固件功能；无需复制SmartCar七目录。

具体建议：

| 当前分类 | 应补全的粒度与边界 |
|---|---|
| F01启动、密码和固定池同页 | 保留启动总览，分启动/依赖、配置校验、资源池与DMA所有权子条目；固定池展开后独立主题页 |
| F02编解码与JSON同条目 | 建立帧/CRC、JSON校验/数值读取子条目；JSON机制单独主题页，保留旧F02入口 |
| F03可靠层与会话 | 分窗口/ACK/重试与SPI/TCP握手两个子条目，说明它们如何组合 |
| F04 SPI及F05网络 | 保留传输职责；SPI拆物理事务/驱动所有权与协议适配子条目；网络拆AP、单控制TCP/BUSY、订阅/UDP及计时 |
| F06～F08桥接 | 当前缺口/已有边界与未来Phase05设计分离，不能把目标状态机当现行分类正文 |
| F09诊断 | 对SPI/NET/池快照分别展开，再说明当前不存在的统一统计边界 |
| F10与validation目录 | 现行工具/方法在guides，历史执行与原始JSON在validation；阶段验收在Phase，不能互相替代 |

保留本项目F01～F10身份，通过子锚点细化，不与SmartCar的F编号混用。分类和物理源码目录不必一一对应；先确定语义主归属，后调整页面与导航，保留旧链接。

### EDA-07 [P3] 当前入口仍带有过期工作状态

证据：[README](../ESP32Bridge/README.md)第23行仍写“未导入未跟踪源码或提交”，而项目已经通过`35e5627`导入，并完成`a0e0917/cba3285`规约及格式注释整改；Docs/index与roadmap已有更新。

[验证指南](../ESP32Bridge/Docs/guides/validation.md)第47行仍称预检“仅是准备结果，未完成源码验收”，同页第49行又给出实际完成结果；[Phase01验证](../ESP32Bridge/specs/features/01-project-foundation/validation.md)第68行的“当前仅清点/规约准备、未整改”与第70～72行实际结果同样并列。known-issues EB-03及最终复核报告已正确记录47文件静态整改/人工复核和187项宿主结果，仅目标构建S5未验证。问题是旧准备段没有明确实施前时点，容易误读，并非最终结果记录缺失。

建议：将README及AGENTS中的前次“本轮”授权/未跟踪说明明确收进带日期的历史记录；验证指南链接最终复核，准备段注明实施前时点。现行入口只给当前状态；保留原历史事实，不把过去未执行改成已经执行，也不把静态整改完成说成目标构建或整体验收完成。
