# 链路联调通用测试流程

本文档沉淀 2026-10-22～23 联调中实际使用且验证有效的测试手段，供后续任何
STM32H7↔ESP32 链路问题复用。所有方法均在本机（Windows + Git Bash）实测通过。
涉及主程序/文档的修改必须同步登记
`Reports/link-validation/20261022-remediation/change-log.md`。

## 0. 角色与硬件事实

- STM32H743 是 SPI **主机**（SPI2，Mode0，8bit，软件 CS=PB12，SCK=PB13，MOSI=PB15，
  MISO=PB14），ESP32-S3 是 SPI 从机；READY=PA15←ESP GPIO14 低有效；
  PD15→EN 保持高电平，任何测试不自动复位 ESP32。
- 每笔事务固定 1024B；低速档 1.875MHz（分频256），高速档 7.5MHz（分频64，
  仅显式调用 `BSP_WiFi_SetFastClock` 切换）。
- ESP32 同时提供 WiFi AP（默认 192.168.4.1）与 USB 串口日志（COM3，115200 8N1）。
- STM32 调试/烧录走 ST-Link SWD；OpenOCD 与串口、WiFi 互不冲突，可并行。

## 1. 烧录

### 1.1 STM32（统一入口，已授权）

```powershell
powershell -NoProfile -File D:\STM32H7\Tools\STM32Flash\flash.ps1            # 生产 Keil HEX
powershell -NoProfile -File D:\STM32H7\Tools\STM32Flash\flash.ps1 -CheckOnly # 只检查不写板
powershell -NoProfile -File D:\STM32H7\Tools\STM32Flash\flash.ps1 -Firmware <其它hex>
```

先在 Keil 编译（`D:\Keil5\UV4\UV4.exe -b SmartCar.uvprojx -j0`，工作目录
`SmartCar/MDK-ARM`），默认烧录 `SmartCar/MDK-ARM/SmartCar/SmartCar.hex`。

测试固件构建与烧录见 `TestFirmware/README.md`。

### 1.2 ESP32（留用户人工执行）

按 `ESP32Bridge/docs/build-and-flash.md`；智能体不代烧。复位可用 pyserial 对 COM3
做 RTS 脉冲（脚本内 DTR/RTS 平时保持 False，避免意外复位）。

## 2. OpenOCD 探针（SWD 被动观察 / 主动干预）

入口（Git Bash，工作目录任意）：

```sh
OOCD=/d/STM32H7/Tools/STM32Flash/openocd/bin/openocd.exe
SCRIPTS=/d/STM32H7/Tools/STM32Flash/openocd/share/openocd/scripts
$OOCD -s $SCRIPTS -f <cfg>
```

cfg 公共头（被动模式，不 halt/复位/写）：

```tcl
source [find interface/stlink.cfg]
transport select hla_swd
source [find target/stm32h7x.cfg]
stm32h7x.cpu0 configure -event examine-end {}
reset_config none
adapter speed 1000
gdb_port disabled
tcl_port disabled
telnet_port disabled
init
# 采样循环示例：echo "...[stm32h7x.cpu0 read_memory 0x2403492c 32 6]..."
```

要点与陷阱（全部实测踩过）：

- 读内存用 `stm32h7x.cpu0 read_memory <addr> <宽度32/8> <数量>`；写用
  `write_memory <addr> 32 <值>`（`mww` 子命令在本版 OpenOCD 报用法错误）。
- halt/resume 用**全局命令** `halt` / `resume`；`stm32h7x.cpu0 halt` 不可用，
  `stm32h7x.cpu0 reg` 也不可用，读 PC 用全局 `reg pc`（取返回值第 3 个词）。
- cfg 里 `proc dump {...}` 会与内建命令冲突报错且行号定位混乱，自定义过程名
  避开内建名（如 `dumpregs`）。
- 脚本中途出错会留下断点和停机状态；任何实验脚本结束前确保 `resume`（必要时
  先 `rbp <addr>` 清断点）。
- 主动实验（写寄存器/脉冲复位）前必须先 `halt`，做完恢复寄存器后 `resume`；
  已验证的代表性实验：RCC APB1LRSTR（0x58024490）bit14 脉冲复位 SPI2
  （`validation/r4-probe/spi2rst-experiment.cfg`）。

### 2.1 关键符号地址（每次构建后必须从 map 重新核对！）

地址随构建漂移。以构建产物 `SmartCar/MDK-ARM/SmartCar/SmartCar.map` 为准：

```sh
grep -E "^    (s_status|s_link|s_consecutive_errors|s_reinit_count|hspi2|hdma_spi2)" \
  SmartCar/MDK-ARM/SmartCar/SmartCar.map
```

R4 固件（HEX af7b5c60…）实测值（示例，重构建即失效）：

| 符号 | 地址 | 说明 |
|---|---|---|
| `s_status` | 0x2403492c | 24B：permits/consumed/completed/errors/timeouts + state 字节(+20) |
| `s_link` | 0x24008f30 | SCB 会话链路状态（24B） |
| `s_consecutive_errors` | 0x240001f8 | R4 连续失败代数 |
| `s_reinit_count` | 0x240001fc | R4 外设重初始化累计次数 |
| `hspi2` | 0x240003fc | State 字节 +129，ErrorCode 字 +132 |
| `hdma_spi2_tx/rx` | 0x24000484 / 0x240004fc | State 字节 +53，ErrorCode 字 +84 |

外设寄存器：SPI2 CR1 0x40003800 / CR2 +04 / CFG1 +08 / CFG2 +0c / IER +10 /
SR +14 / IFCR +18 / RXDR +30；DMA1 LISR 0x40020000、Stream1(TX) CR+28 NDTR+2c、
Stream2(RX) CR+40 NDTR+44；DMAMUX1 ch1 0x40020804、ch2 0x40020808、
CSR 0x40020880；RCC APB1LRSTR 0x58024490（SPI2RST=bit14）；GPIOA_IDR 0x58020010。

现成 cfg 模板：`Reports/link-validation/20261022-remediation/` 下
`baseline/backlog-probe.cfg`（被动计数采样）、`validation/r4-probe/observe.cfg`、
`validation/r4-onboard/observe-10min.cfg`（10 分钟长跑）、
`validation/r4-probe/spi2rst-experiment.cfg`（主动外设复位实验）。

### 2.2 判读基准（健康 vs 死循环）

- 健康：completed 持续增长（低速约 80 笔/秒有负载时）、errors/timeouts 不动、
  backlog=permits−consumed ∈ {0,1}、SR 常态 0x10002。
- OVR 死循环（2026-10-23 实锤签名）：errors 约 5/秒持续增长、completed 冻结、
  SR=0x18007、TXNDTR 冻结 0x3d7、RXNDTR=0、LISR=0x10000(FEIF2)、
  hspi2.ErrorCode 在 0↔0x44(OVR|ABORT) 循环，state 3→0 反复但永不治愈。
- R4 自愈签名：errors 恰好停在 3 的倍数、REINIT≥1、CONSEC=0、completed 恢复增长。

## 3. ESP32 串口被动采集

```sh
python Reports/link-validation/20261022-remediation/baseline/serial_capture.py <输出目录> <秒数>
```

读 COM3 115200 8N1，不触发复位；串口独占，两个采集不能并发。
判读：`spi` 5 秒行的 invalid/crc/osync 恒 0、`queue` 无持续增长、`bridge` 行无
orphan/backpressure 累积（R6 后含完整计数）。

## 4. PC 侧业务验证（SmartCarLink）

```sh
cd Tools/SmartCarLink
python smartcar_link.py params get     # 控制连接读参数（端到端协议验证）
python smartcar_link.py monitor        # 独占控制连接并打印遥测（用于 BUSY 测试）
python smartcar_link.py dump ...       # 日志导出，核对总长与 CRC32
```

- G-01 BUSY 回归：先起 monitor 占住控制连接，再开第二个 `params get`；
  期望第二个连接收到明确 BUSY 或被关闭，而不是连接成功但永久无字节。
- PC 负载发生器：`TestFirmware/scripts/pc_load.py <秒数> [启动延迟]`。
- 3.3V 轨：ST-Link 采样仅作参考（实测 3.54~3.61V），正式结论用万用表人工复核。

## 5. 标准验证矩阵（改链路相关代码后必做）

1. 宿主：SmartCar 八入口（见 `SmartCar/specs/features/16-spi-wifi-link/validation.md`
   的命令清单）；无 MinGW gcc 时用 Clang/LLD 替代宿主探针
   （`Reports/link-validation/20261022-remediation/r4-build/clang_host_probe.py`），
   必须如实标注"替代宿主，非 GCC"。
2. Keil AC5 全量构建 0 错误 0 警告，记录 Code/RW/ZI 增量与 HEX SHA256。
3. 烧录后被动观察 ≥10 分钟：errors/timeouts 不增、backlog≤1、completed 增长；
   有自愈机制的版本允许 REINIT 增加但 errors 必须停在小整数。
4. params get×2、BUSY 回归、monitor 遥测、dump CRC。
5. 证据按 `Reports/link-validation/20261022-remediation/validation/<批次>/`
   归档，原始日志不删改。
