# AGENTS.md

本文件只约束 `SmartCar/` 固件及其工程配置、规约；仓库根目录的 Git 同时管理硬件和参考资料。开始固件工作前，先读本文件，再按顺序阅读：

1. `specs/mission.md` — 项目为什么存在
2. `specs/techstack.md` — 技术约束（含硬性约束，不可违反）
3. `specs/roadmap.md` — 当前进度与下一步

## 工作规则

- 实现代码前必须存在对应的功能规约（`specs/features/NN-*/`）；没有规约的功能先写规约再动手。
- **规约提交先于代码，禁止倒序补文档**：任何新增、修改、修复、重构、删除代码或工程配置的工作，包括不改变运行行为的机械重命名，都必须先完成对应规约修改、消除全部未决设计项，并将规约作为不含实现代码的独立提交；该提交完成后才允许修改实现。仅执行只读调查、构建验证或收集现状证据时可以不改规约。
- **规约必须与代码一一对应且表述可判定**：至少写明需求编号、目标行为、影响文件与符号、输入/输出、状态或时序变化、错误路径、兼容性要求和验证方法；不得使用“适当处理”“按需调整”“视情况而定”“后续完善”等无法直接指导实现和验收的措辞。
- **不确定即暂停并询问用户，禁止擅自决定**：凡是存在多种合理实现、资料互相矛盾、硬件事实无法从仓库确认，或会影响外部行为、控制参数、状态机转移、接口/协议、数据格式、存储兼容性、实时性、安全性及休眠代码去留时，必须在写代码前列出已确认事实、具体疑问、可选方案及影响，等待用户明确选择。可以给出推荐及理由，但推荐不等于授权，不得以“暂定”“默认采用”代替用户确认。
- **确认交互优先使用弹窗**：需要用户在候选方案中选择或确认时，优先使用产品提供的选择弹窗；若当前运行模式不支持弹窗，必须明确说明限制，并改为一次只询问一个必要问题，不得用大段普通文本同时要求用户处理多个决策。
- **实施中发现新歧义同样暂停**：若编码或验证过程中发现规约遗漏、实现与规约冲突或新的决策点，停止该决策点相关实现，先更新规约草案并询问用户；收到答复后把决定、理由和日期回填规约，再继续编码。
- **变更完成后保持可追溯**：同步更新关联的 `requirements.md` / `plan.md` / `validation.md` / `roadmap.md` / `CHANGELOG.md`；验证文档必须记录实际执行结果，且每条需求都能定位到实现文件/符号和至少一个验证项，防止文档与代码漂移。
- 每个任务分组完成后运行对应 `validation.md` 中的自动化验证（基线：`MDK-GCC/build.sh` 构建零警告）。
- **接入任何当前未启用的赛道元素或休眠代码前，必须逐个与用户确认设计**（用户明确要求）；确认结论回填到对应规约后再实现。
- 已知缺陷与整改排期见 `specs/roadmap.md`；不要顺手在别的任务里“顺带修”。阶段顺序以路线图中记录的最新用户决定为准，不能用旧优先级覆盖它。
- Git 操作遵守下文「Git 约定」。

## Git 约定

- **仓库根是 `../`**：先检查全仓库状态，仅按本任务的明确路径暂存并检查暂存差异，不得混入 `../Hardware/`、`../引脚分配/` 等其他在途改动；遵守根目录 `AGENTS.md` 的 Git 边界。
- **规约与实现分次提交**：功能分支 `feature/NN-<name>` 的顺序是规约三件套的独立提交 → 实现提交（可按任务组拆分）→ 验证结果及 CHANGELOG 回填。后续小改动同样先单独提交规约增量，再改代码；不能把规约和该批实现放在同一提交。默认只 commit 不 push；push 必须由用户明确要求。
- **宪章与路线图**：`specs/mission.md`、`specs/techstack.md` 的治理修改，以及新增阶段或重大重排，走 `chore/constitution-<topic>` 独立分支并作纯文档提交。`specs/roadmap.md` 的阶段勾选和日常进度回填可随对应功能分支提交；大规模再规划走 `chore/replan-<topic>`。
- 提交信息由智能体起草（中文、说明动机与关联 Phase）。每次提交前向用户展示文件清单、差异摘要和提交信息；完成范围检查后可自动 commit，无须逐次等待提交许可。涉及前述未决设计事项仍须先得到用户明确决定。
