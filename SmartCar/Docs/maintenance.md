# Docs 分类与维护契约

2026-11-07用户确认；执行依据为[修复方案](../../Reports/smartcar-documentation-system-repair-plan-2026-11-07.md)。前层治理约束完整 Phase，Docs 与当前代码按功能和实现语义双向对应。

### 4.3 Docs 功能条目最低内容

每个 F 条目必须能独立解释功能，协作机制可引用其他主条目，不要求每个 C/H 一篇。

| 项 | 必须写清的内容 | 不合格示例 |
|---|---|---|
| 功能和启用条件 | 用途、正常/测试模式、编译开关、缺失能力及休眠边界 | 只列“有 PID / 有 IMU” |
| 输入与输出 | 类型、单位、标度、来源、有效性、哨兵和更新时机 | 只有函数签名 |
| 实现原理 | 公式、分支、计算和转换顺序、必要伪代码及设计依据 | “详见源码”“按原逻辑” |
| 调用与调度 | 初始化、前台、ISR、周期、优先级、先后关系及依赖 | 只有模块目录树 |
| 状态和并发 | 状态持有者、写入/读取方、复位条件、锁/快照/发布顺序 | 把 const getter 当作一致快照 |
| 参数与配置 | 见 4.4，写出影响行为的值、表和条件 | 只给配置表所在文件 |
| 错误与兼容 | 失败输出、副作用、重试/降级、数据布局与旧版兼容 | 只描述成功路径 |
| 源码定位 | 实际路径、关键函数/类型/宏/表；协作模块主归属 | 只列不存在或旧目录的符号 |
| 来源与验证 | 相关 Phase/FR/TC、实际证据、尚未验证事项 | 用历史编译通过证明当前实车正确 |

小型 getter 可归入模块接口表；复杂算法、状态机、跨中断队列和持久化路径必须有展开说明。全局功能概览、架构页和功能页分别承担全局与局部阅读，不把全部细节堆进索引。

### 4.4 关键参数登记规则

各功能页维护参数表；另建 `Docs/parameters.md` 提供全局分类、适用模式、主条目及源码入口。全局页只作索引，实际数值在功能页完整呈现，并与源码同步核对。

每项至少包含：文档身份、含义、真实符号/字段、类型、单位/算法标度、默认值、范围与约束、初始化来源、运行时修改来源、覆盖优先级、生效时点、持久化/版本关系、适用模式、源码及 Phase 来源。不适用写原因；无法确认的物理单位和阈值依据标未知并提问，不编造标定结论。

“默认值”不能冒充“当前运行值”：必须说明 Flash 恢复、档位、模式、状态配置、菜单/UART/SCB 临时覆盖的影响。对关键配置矩阵和结构布局应直接展示值/偏移，不能因怕重复而只贴源码链接。

强制覆盖类别：

1. 调度周期、优先级、预算、超时、窗口长度和队列容量。
2. 采集量程、标度、滤波、标定、有效阈值与通道/引脚对应。
3. 控制增益、基础速度、限幅、死区、状态配置表、元素门限和停车判据。
4. 参数镜像、Flash 布局、CRC、版本/迁移、日志字段/容量、协议长度和字节序。
5. 默认模式/档位、编译选项、LCD 选择、独立板测选择及条件分支。

### 4.5 三段追溯

1. 治理条款 → Phase FR/TC：由 Phase“背景与约束”指明本次适用条款；不为每项建立庞大新编号体系。
2. Phase FR/TC → Docs 功能条目：`Docs/traceability.md` 维护全局关系和阶段基线/替代状态；Phase 本身仍保留完整需求与设计。
3. Docs ⇄ 代码：功能页保存实现与参数定位，`Docs/architecture.md` 提供模块反查，`Docs/parameters.md` 提供参数反查。先通过外部文档建立映射，不为增加 Docs 入口批量修改 C/H 注释。

发现 Docs 与代码不同，先区分是否属于第1.3节已登记的本组短暂领先；属于时按已批准目标继续同步，不把目标反改为旧实现。除此之外的失配按当前代码更正事实说明，同时登记与已批准 Phase 的差异；修复目标仍须经用户决定。代码事实不等于设计批准，旧设计也不等于当前能力。

### 4.6 Docs 分类、粒度与目录完善

#### 4.6.1 分类依据与当前问题

现有分类总体沿用固件职责，保留七个领域目录，不按 Phase、源码文件数量或缺陷编号重新分组。当前需要修正的是领域内主题粒度和跨域边界：F26把ADC/编码器/PWM混在一起，F29把时钟/DMA/多种器件驱动混在一起，F08把多种控制器和电机执行混在一起；另一边UART、DL1B又是单项。结果是读者能找到大概位置，却仍需在压缩段落和源码中自行还原完整功能。

分类分为四个层次，不能把它们混成同一个编号体系：

| 层次 | 分类依据 | 约束 |
|---|---|---|
| 领域目录 | 固件的稳定职责与抽象层次 | 保留system/sensing/control/services/hmi/platform/guides，不随阶段或源码搬迁而改名 |
| 主题页 | 能独立理解和修改的一项功能、机制或完整操作场景 | 同页内容应共享主要数据流、状态/参数和验收目标；不按每个C/H机械拆页 |
| F编号及子条目 | 稳定的功能身份与细分定位 | 保留F01～F33；拆细旧功能时增加子锚点，不把目录、页数和F编号绑定 |
| 源码映射 | 实际实现位置和协作关系 | 一个主题可对应多个模块，一个模块可参与多主题；实现和状态的详细说明各有明确主归属 |

主题拆分条件：存在独立输入输出、主要状态或配置、错误语义及验证目标，且读者会单独查阅或修改。满足这些条件就拆页；只是一组共享算法的小型getter、薄转发或私有辅助函数则留在主题内部。页长仅是阅读提示，不作为硬性拆分阈值。

#### 4.6.2 七类职责边界

| 目录 | 主说明范围 | 跨域内容如何连接 |
|---|---|---|
| `system/` | 启动、生命周期、运行调度、模式切换、停车及安全编排 | 描述何时调用感知/控制/服务，不重复算法公式或外设寄存器流程 |
| `sensing/` | 将原码转换为业务观测量：电感偏差、灰度标定/质心、姿态、滤波等 | 原码采集、通道/rank/引脚和驱动返回语义链接platform；保护动作链接system |
| `control/` | 观测到控制意图/执行值：控制器、双模式协调、状态配置、元素与休眠控制 | 说明业务PWM/方向/里程语义；物理输出、CCR和极性实现链接platform |
| `services/` | 参数、持久化、日志、通信、上传及导出等业务服务 | 日志格式/会话/导出状态归日志主题；帧封装/ACK/可靠传输归通信主题；SPI物理/DMA驱动归platform |
| `hmi/` | 用户操作、页面、按键分发、显示与编辑流程 | 按键电气采集归platform；参数实际生效/保存归services；不能因有菜单就把业务规则放到HMI |
| `platform/` | 板级资源、驱动、原始采集与执行、时钟/DMA、共享总线、独立板测机制 | 正常业务算法链接sensing/control；板测操作步骤可由guides引用机制，不复制实现细节 |
| `guides/` | 构建、烧录、配置切换、验证工具和证据维护方法 | 引用AGENTS/code-style的现行政策和Phase的本次验收；不另创一套治理规则 |

跨域功能按“主要机制在哪里”确定主说明；从其他领域保留协作链接。例如灰度原始完整帧发布归platform，标定和质心归sensing，失线后停车归system，不能把三者当成三份相互竞争的灰度算法说明。

#### 4.6.4 功能身份、主归属与旧链接兼容

1. 保留F01～F33身份；F26、F29这类宽功能保留父级总览，细节用上述稳定子锚点表达。拆页本身不新增F34，也不重编号旧功能。
2. F父条目负责功能范围、子功能和协作总览；子主题负责自己的算法、状态、参数、错误及源码定位。父页引用子页，不复制成另一套完整说明。
3. `traceability.md`增加“父功能/具体子条目/主说明/源码主归属”字段。一个FR指向其实际涉及的子条目，确实跨域时列多个，不把父级总览当作所有需求的唯一终点。
4. `architecture.md`逐模块登记主要职责及协作条目；每个关键符号/状态/参数确定一处详细说明归属。跨页出现只作必要上下文及链接，不重复维护值表。
5. 旧文件保留现存显式锚点和已有被引用的章节入口，注明详细内容的新位置。主要导航切换到新页；旧链接仍能到达明确的对应内容，不仅跳到新的总首页。
6. Phase历史正文和原始证据中的路径不批量改写；现行导航、可复制模板及必要承接说明更新到新主条目，保留当时基线含义。
7. 文件移动不改变F身份；以后新增实际功能才建立新的F身份。一个新Phase可以修改多个旧F，一个F也可由多个Phase演进，不建立Phase号与F号一一对应关系。

#### 4.6.5 全局阅读入口

- `index.md`提供按领域的能力总览及推荐阅读顺序，说明正常模式、测试模式、启用/休眠与限制；不能只给一串文件链接。
- `architecture.md`提供整体启动/运行/停车数据流、依赖和模块反查；目录结构不能替代运行链说明。
- `traceability.md`提供前层约束/Phase需求到功能父项及子项的追溯；阶段完整设计继续在Phase。
- `parameters.md`提供按采集、控制、保护、存储、通信、HMI及板测分类的参数反查。链接须指向主主题的具体参数表，而不是宽泛父页。
- `known-issues.md`提供当前实际缺陷与待验限制，回链受影响主主题和阶段；缺陷编号不作为功能目录分类依据。

#### 4.6.6 分类迁移步骤

先登记旧页/旧锚点→新主题/新锚点的清单，再在当前样板中落实F08/F12和F33粒度；样板核对通过后，完成平台与感知拆页、参数/临时调参分离，最后统一全局索引和兼容入口。每批正文迁移与相关链接调整一并完成；不先删旧页等待后续补链，不借分类迁移重写算法或验证历史。


## 5. 后续一次变更的标准流程

以下流程已按2026-11-07用户确认的D05定稿；本方案实际落地时须同步治理文件及模板，不能仅修改本报告而宣称全仓规则已完成纠偏。

1. 检查仓库状态；读前层文档，确认任务范围、阶段位置及约束；读关联 Phase、Docs，再核对源码。
2. 在新 Phase，或尚在进行的 Phase 新任务组，定义问题、目标、设计、文件/符号、参数/状态/兼容变化与验收。
3. 在本次 Phase 附属设计中保存受影响 Docs 的目标草案，写明拟修改的功能条目；未决设计由用户决定。
4. 独立纯规约提交：Phase 三件套、必要设计及治理增量。未开工组的 Docs 目标草案继续保存在 Phase。
5. 每组开工时，先更新对应 Docs 的功能、算法、接口和关键参数，按第1.3节标明本组同步状态；随后紧接着修改代码。Docs 比代码先一个编辑步骤，不跨多组预写未实现能力。
6. 从 Phase 验收需求，从 Docs 审查实现，从代码反查 Docs 覆盖；按当前政策执行审查、适用构建与 R08。
7. 组完成前消除本组Docs/代码失配并取消同步中标记；实现提交须带匹配的 Docs。本次 Phase 同步或紧接着记录实际验证结果、证据和偏差，更新 roadmap/CHANGELOG；中断则如实登记尚未同步的部分。
8. 软件完成、硬件待验和阶段交付关闭分别记录。下一次独立演进新增 Phase，并保留本次设计与结果。

Docs-only 的说明纠错可以独立纯文档提交；若调查发现代码必须改，则另按规约先行办理。不能为了“互译”随手修复已有固件问题。
