# 使命（Mission）

## 愿景

打造一套基于 **STM32H743VIT6** 的智能车竞赛固件平台：以 STC AI8051U 省赛工程（`Material/Sirius20260718`，逐飞库）为电磁循迹算法基线，支持可切换的 16 路模拟灰度光电循迹、双传感器保护与完整运行记录，为竞赛备赛提供可持续迭代的代码基座。阶段进度与实机待验状态统一见 [roadmap](roadmap.md)。

## 目标用户 / 受众

- **参赛队员（含未来的自己）**：赛前调参、赛后复盘的主要使用者，依赖菜单/串口调参与数据记录快速定位问题。
- **维护者（未来的自己）**：间隔数周后回到代码库时，依靠 `specs/` 规约恢复全部上下文。
- **指导教师 / 评审**：通过 README 与规约文档了解系统设计依据。

## 范围

本宪章和 `specs/` 文档体系只治理 `SmartCar/` 固件。仓库根目录同时管理硬件、引脚和参考资料；这些目录的独立任务不适用固件功能规约流程。

### 范围内（In Scope）

- 电磁循迹控制链：4 路电感采集、加权差分归一化偏差、方向环、差速分配、速度闭环。
- 光电循迹演进：16 路模拟复用灰度采集、手工黑底/白线标定、加权质心偏差；光电和电磁各有参数与状态机，由选中模式执行控制，另一套继续判断并记录状态。首版光电只含普通循迹和保护，设计见 Phase 14。
- 赛道元素识别与处理：十字、环岛、跷跷板、路障等元素的判断与状态机（含逐步接入未启用元素）。
- 车载人机交互：LCD 菜单/仪表盘、ADC 分压按键、串口无线调参、双档参数管理。
- 参数持久化与运行数据记录（板载 W25Q64），支撑赛后分析。
- 支撑上述功能的 BSP 驱动层与运行时调度架构（三线中断契约）。

### 范围外（Out of Scope）

- 摄像头 / 图像视觉循迹方案；Phase 14 的反射式灰度阵列属于光电传感器，不引入摄像头或图像处理。
- PC 端工具的实现与维护不由本固件宪章治理。仓库已有独立的 [`Tools/SmartCarLink`](../../Tools/SmartCarLink/README.md) 命令行工具；固件负责其对应协议和车端业务，不能把该范围边界解释为全仓库禁止开发电脑端工具。
- 硬件电路设计（原理图/PCB 资料在仓库 `../../Hardware/` 与 `../../Material/引脚分配/`，另行管理，本目录只覆盖固件）。
- 逐飞 STC 库本身的维护（`../../Material/Sirius20260718/` 作为仓库内的一次性码源快照，仅供算法出处对照，不按本固件的 SDD 阶段持续维护）。

## 语气与风格

- 文档使用**严谨、简洁的中文**；技术术语保留英文原词（如 PID、DMA、ISR）。
- 描述现状时如实记录（包括缺陷与未启用功能），描述目标时给出可检验标准；不写"工作正常"这类无法判定的表述。

## 成功标准

1. **稳定完赛**：现有电磁模式维持循迹与已启用元素；双模式演进按规约验证光电普通循迹、任一传感器失线停车、日志异常停车及低压保护。双保护要求赛道同时提供有效的白线黑底和电磁信号，不能把单一赛道信号当成双模式验收环境。
2. **参数可调可追溯**：调参结果掉电不丢，每次变更能回答"哪版参数、为什么改"。
3. **数据可复盘**：跑完即可导出结构化数据（CSV），支撑赛后分析。
4. **规约与代码同步**：任何功能变更先过规约、后有代码，文档与实现不漂移。
5. **新元素小步接入**：新增/启用一个赛道元素是一次可审查的功能循环，不引发既有功能回归。

## 项目治理原则

### 1. 文档先行

除只读调查、现状取证和不改变仓库内容的构建验证外，所有代码新增、修复、重构、删除与配置调整都必须先修改规约。规约修改至少覆盖：

- `requirements.md`：背景、编号需求/约束、用户决定、行为边界、错误与兼容要求。
- `plan.md`：详细设计、文件/符号映射、任务组、顺序、依赖、风险和回退；复杂设计可用本阶段附属文件。
- `validation.md`：验证输入/条件、方法、预期和通过标准，实施后记录实际结果及证据。
- `Docs/`：现行功能及实现说明，按下述顺序维护。
- roadmap / CHANGELOG：实际状态、依赖与已发生变更，不以文档完成代替硬件验收。

### 2. 完整阶段与现行说明

前层治理文档 → Phase → Docs ⇄ 代码。Phase 完整保存背景、需求、详细设计、用户决定、实施计划、文件与符号映射、验证标准和实际结果，按该阶段基线解释；Docs 说明当前固件功能、算法、状态、时序、参数、错误与兼容性。功能语义对应不要求逐行翻译。阶段显式关闭后的独立修改新增 Phase；进行中的阶段可以补充任务组，软件完成但硬件待验不自动视为关闭。

Phase 确认并独立提交 → 先更新本组 Docs → 紧接着实现代码 → 双向核对 → 匹配 Docs 与代码同批交付。目标草案与未开工组设计保存在 Phase；本组 Docs 短暂领先时标明“本组实现同步中”、Phase/任务组及更新前代码基线，完成前取消标记。

Phase 设计须说明输入输出、影响文件和符号、状态时序、错误、兼容及验收；Docs 必须能解释实际实现。未决设计未清空前不得修改实现。

### 3. 用户拥有未决事项的最终决定权

遇到下列任一情况，实施者必须暂停相关设计或编码并询问用户，不得自行选择：

- 两种或以上方案均能满足表面需求，但会产生不同运行行为或维护成本；
- 仓库文档、代码、原理图、实测现象之间存在冲突；
- 硬件型号、接线、极性、量程、机械结构或赛道规则无法从现有证据唯一确定；
- 涉及控制参数、状态机条件、元素处理策略、实时调度、安全停车、故障降级；
- 涉及公共接口、串口协议、数据格式、Flash 布局、旧数据兼容或工具链约束；
- 涉及启用、删除、替换休眠代码或改变当前已存在但未验证的行为；
- 验证失败存在多个可能修复方向，选择会改变系统语义。

询问时必须提供已确认事实、尚不确定的具体问题、候选方案、各方案影响和有依据的推荐。推荐仅供用户决策，只有用户明确答复后才能视为定稿。用户决定须连同日期、适用范围和理由回填到对应规约，之后才能继续实施。

存在多个候选方案时，优先通过产品提供的选择弹窗请求确认；当前运行模式不支持弹窗时，须说明限制并一次只提出一个必要问题，避免用户在普通文本中同时处理多个决策。

纯机械且不改变既定语义的实现细节，可以依据已确认规约执行；一旦无法证明其不改变语义，仍按不确定事项处理并询问用户。

### 4. 分支与提交

- 治理宪章的修改、新增阶段或路线图重大重排在独立宪章分支作纯文档提交；阶段勾选与日常进度回填可随对应功能分支提交。
- 智能体每次提交前展示本次文件清单、差异摘要和提交信息，核对暂存内容只含本任务文件后可自动提交。用户对未决设计拥有决定权；该决定权不等于每次提交都须再次获得许可。未经明确要求不推送远端。

## 验证与文档职责（2026-10-31）

后续开发强制保留格式/命名、注释准确性、上下文逻辑审查、当前配置固件零警告编译和 R08 人工证据/提交前检查。其余软件脚本按变更目标选取，优先复用，尽可能减少新增测试脚手架；真实硬件模块测试及相关板上验收保留。完整执行规则以 [AGENTS 的验证要求](../AGENTS.md#验证要求2026-10-31-起) 为准。

本决定不取消需求—实现—验证追溯；逻辑审查可作为明确的验证项，必须记录审查对象与结论，不能写成未执行测试已通过。既有脚本、历史结果及硬件待验项保持；纯文档变更不要求固件构建或软件行为回归。

主文档分工：mission 定义目标与治理原则；techstack 记录技术选型和硬性约束；code-style 定义写作标准；AGENTS 定义协作执行步骤；roadmap 汇总当前进度与剩余工作；CHANGELOG 记录各时点已发生变更；README 提供使用入口。现行功能和实现说明由[Docs](../Docs/index.md)维护；所属 Phase 完整保留该次需求、详细设计、映射、计划、决定及验收。通过[功能索引](../Docs/traceability.md)连接两层，不在主文档复制完整内容。历史决定注明日期和适用阶段，不能覆盖后续明确决定。
