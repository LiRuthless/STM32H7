# 使命（Mission）

## 愿景

打造一套基于 **STM32H743VIT6** 的电磁循迹智能车竞赛固件平台：将已在省赛验证的 STC AI8051U 工程（`Sirius20260718`，逐飞库）的循迹控制算法，迁移到性能余量更大的 H7 平台，并在此基础上持续演进——更快的控制链路、更完善的调参工具、更可靠的赛道元素处理，为竞赛备赛提供可持续迭代的代码基座。

## 目标用户 / 受众

- **参赛队员（含未来的自己）**：赛前调参、赛后复盘的主要使用者，依赖菜单/串口调参与数据记录快速定位问题。
- **维护者（未来的自己）**：间隔数周后回到代码库时，依靠 `specs/` 规约恢复全部上下文。
- **指导教师 / 评审**：通过 README 与规约文档了解系统设计依据。

## 范围

本宪章和 `specs/` 文档体系只治理 `SmartCar/` 固件。仓库根目录同时管理硬件、引脚和参考资料；这些目录的独立任务不适用固件功能规约流程。

### 范围内（In Scope）

- 电磁循迹控制链：4 路电感采集、加权差分归一化偏差、方向环、差速分配、速度闭环。
- 赛道元素识别与处理：十字、环岛、跷跷板、路障等元素的判断与状态机（含逐步接入未启用元素）。
- 车载人机交互：LCD 菜单/仪表盘、ADC 分压按键、串口无线调参、双档参数管理。
- 参数持久化与运行数据记录（板载 W25Q64），支撑赛后分析。
- 支撑上述功能的 BSP 驱动层与运行时调度架构（三线中断契约）。

### 范围外（Out of Scope）

- 摄像头 / 视觉循迹方案（本项目为纯电磁方案）。
- PC 上位机软件（调参与数据分析复用串口工具 / 逐飞助手 / Excel，不自建上位机）。
- 硬件电路设计（原理图/PCB 资料在仓库 `../Hardware/` 与 `../引脚分配/`，另行管理，本目录只覆盖固件）。
- 逐飞 STC 库本身的维护（源工程仅作算法出处参照，不在本仓库内）。

## 语气与风格

- 文档使用**严谨、简洁的中文**；技术术语保留英文原词（如 PID、DMA、ISR）。
- 描述现状时如实记录（包括缺陷与未启用功能），描述目标时给出可检验标准；不写"工作正常"这类无法判定的表述。

## 成功标准

1. **稳定完赛**：在标准电磁赛道上稳定完成循迹与已启用元素，低压/失控有保护。
2. **参数可调可追溯**：调参结果掉电不丢，每次变更能回答"哪版参数、为什么改"。
3. **数据可复盘**：跑完即可导出结构化数据（CSV），支撑赛后分析。
4. **规约与代码同步**：任何功能变更先过规约、后有代码，文档与实现不漂移。
5. **新元素小步接入**：新增/启用一个赛道元素是一次可审查的功能循环，不引发既有功能回归。

## 项目治理原则

### 1. 文档先行

除只读调查、现状取证和不改变仓库内容的构建验证外，所有代码新增、修复、重构、删除与配置调整都必须先修改规约。规约修改至少覆盖：

- `requirements.md`：用编号需求定义必须实现的行为、边界条件、故障处理和兼容性要求；
- `plan.md`：列出将修改的文件与符号、修改顺序、依赖关系、风险和回退条件；
- `validation.md`：为每条需求提供可执行的自动化或人工验证步骤和唯一通过标准；
- `roadmap.md`：反映阶段状态、依赖和优先级变化；
- `CHANGELOG.md`：在实现完成时记录用户可感知或工程治理层面的变化。

在上述文档尚未达到可直接指导编码和验收的程度前，不得开始修改实现代码，也不得先写代码再补文档。每批实现改动（包括纯机械重命名）对应的规约须先作不含实现代码的独立提交，完成该提交后才可修改实现；验证结果与阶段进度在实施后如实回填。

### 2. 文档与代码一一对应

规约中的每条实现需求必须能够回答以下问题，且答案必须唯一、可核对：

1. 为什么修改，现状证据是什么；
2. 修改哪些文件、函数、全局量、宏、结构体、状态或中断路径；
3. 输入、输出、单位、取值范围、默认值和失败返回分别是什么；
4. 正常路径、边界路径、异常路径和降级行为分别是什么；
5. 是否改变控制周期、中断优先级、硬件资源、通信协议、持久化格式或既有实车行为；
6. 用哪个验证项证明需求已实现，实际结果记录在哪里。

不得使用无法判定实现完成与否的模糊描述。代码完成后，需求编号、实现位置和验证项之间必须可以双向追溯。

### 3. 用户拥有未决事项的最终决定权

遇到下列任一情况，实施者必须暂停相关设计或编码并询问用户，不得自行选择：

- 两种或以上方案均能满足表面需求，但会产生不同运行行为或维护成本；
- 仓库文档、代码、原理图、实测现象之间存在冲突；
- 硬件型号、接线、极性、量程、机械结构或赛道规则无法从现有证据唯一确定；
- 涉及控制参数、状态机条件、元素处理策略、实时调度、安全停车、故障降级；
- 涉及公共接口、串口协议、数据格式、Flash 布局、旧数据兼容或工具链约束；
- 涉及启用、删除、替换休眠代码或改变当前已存在但未验证的行为；
- 验证失败存在多个可能修复方向，选择会改变系统语义。

询问时必须提供已确认事实、尚不确定的具体问题、候选方案、各方案影响和有依据的推荐。推荐仅供用户决策，只有用户明确答复后才能视为定稿。用户决定须连同日期、适用范围和理由回填到对应规约，之后才能继续实施。

存在多个候选方案时，优先通过产品提供的选择弹窗请求确认；当前运行模式不支持弹窗时，须说明限制并一次只提出一个必要问题，避免用户在普通文本中同时处理多个决策。

纯机械且不改变既定语义的实现细节，可以依据已确认规约执行；一旦无法证明其不改变语义，仍按不确定事项处理并询问用户。

### 4. 分支与提交

- 治理宪章的修改、新增阶段或路线图重大重排在独立宪章分支作纯文档提交；阶段勾选与日常进度回填可随对应功能分支提交。
- 智能体每次提交前展示本次文件清单、差异摘要和提交信息，核对暂存内容只含本任务文件后可自动提交。用户对未决设计拥有决定权；该决定权不等于每次提交都须再次获得许可。未经明确要求不推送远端。
