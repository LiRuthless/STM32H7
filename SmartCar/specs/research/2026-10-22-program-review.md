# SmartCar 全程序审查报告

日期：2026-10-22。代码基线：`17ce75d99d63bb23eacdc5402d21c55d9a1dcf11`。

> 2026-10-31现行导航：[方向控制F08](../../docs/control/tracking-and-controllers.md#f08)、[问题台账](../../docs/known-issues.md)。以下源码位置/复现结果均属于原审查基线，不作为现行逐符号索引；本轮未重验这些结果。

## 结论

当前程序能够通过两种 LCD 配置的 GCC 编译，但存在控制数值、异常等待、串口解析及参数状态一致性问题。优先处理方向输出限幅顺序和高优先级中断中的阻塞超时。编译及已有回归通过不能证明这些错误路径正确。

本次只调查、验证并生成报告，没有修改实际固件、工程配置、标定值或阶段验收状态。硬件目录已有改动未参与本次审查。以下建议不是已批准的实现方案；后续修复须按项目规则先明确行为并提交规约。

## 范围与方法

- 检查 App 控制、双模式状态机、参数、菜单、串口、SCB、调参、日志与上传链，BSP 采集、总线、存储和显示接口，以及相关 Core 初始化、中断、链接配置。
- 对照宪章、写作标准和相关 Phase 需求；区分历史 as-built 行为、已确认保留项及当前增量要求。
- 在 `MDK-GCC/build/audit-20261022/SmartCar/` 建立审查副本执行构建，避免覆盖工作区已跟踪的 ELF 和历史测试证据。
- 复用真实 C 宿主夹具，增加临时边界输入验证。宿主测试的传感器/Flash/PWM 是替身，不等于实车测试。未逐行审计全部第三方 HAL/CMSIS，仅追查有关调用实现；本报告也不替代 CS-01～15 逐函数完整验收。

路径和行号均相对 `SmartCar/`，对应上述基线。

## R01：方向限幅前发生窄化，合法参数可产生反向输出

位置：`App/pid.c`（原基线137～169，旧文件位置作为历史证据保留），尤其第 158 行；参数允许范围见 `App/scb_protocol.c::SCB_ValidateValues`。

`PID_DirectionStep` 把浮点和直接赋给 `int16_t pid_out`，之后才判断是否超过 ±1000。超过 int16 可表示范围时，后续限幅已经无法恢复正确数值和符号。

最小触发输入：`error=100`、`history=0`、`accel=0`，增益 `{kp=0,k2p=4,kd=0,k2d=1}`。光电误差 100 在合法范围内，K2P=4 也在 SCB 允许的 0～100 内。数学输出为 40000，正确饱和值应为 +1000；本次真实 C 宿主执行得到 **-1000**。

本次 GCC ARM 产物中也确认顺序为 `vcvt.s32.f32` → `sxth` → 与限幅值比较，问题并非仅由宿主替身产生。C 层面的越界浮点转整数也不应依赖某个编译器的表现。

影响：调参后可能向相反方向分配轮速。当前 `runtime_tuning.py` 的 `expected()` 同样先转换为 int16，可能把错误顺序当成预期，且最大参数测试主要验证查询编码，没有覆盖这个数值边界。

建议：先在足够宽的数值域内检查有限性和限幅，再转换输出；增加正负越界、极值增益、误差跳变测试，期望值按数学饱和计算。该顺序在历史行为保持规约中被保留过，修复必须明确更新相应契约。

## R02：高优先级中断中的 HAL 阻塞超时可能失效

位置：`App/app.c:373`、`BSP/bsp_dl1b.c:46～49`、`BSP/bsp_sampler.c:180～184`、`BSP/bsp_imu660rb.c:87～94`。

证据链：

1. TIM6 和 TIM15 的抢占优先级都是 0；`Core/Inc/stm32h7xx_hal_conf.h:169` 的 SysTick 优先级也是 0，使用 NVIC_PRIORITYGROUP_4。
2. TIM6 调用 `BSP_DL1B_Update`，内部为阻塞 `HAL_I2C_Mem_Read/Write`；TIM15 内阻塞读取 IMU SPI。
3. HAL SPI/I2C 的等待循环通过 `HAL_GetTick()` 与起始 tick 的差判断超时。SysTick 不能抢占同级正在执行的中断。
4. 若总线或外设状态卡在必须依靠超时退出的等待条件，tick 不推进，传入的 10ms 并不构成有效退出上界。

影响：控制/采样中断可被卡住，TIM7 低压保护及喂狗也不能运行；PWM 可能保持故障前输出直到独立看门狗复位。`App_ControlISR` 末尾的 DWT 900μs 检查只有在调用返回后才执行，无法中断内部死等。不能笼统声称“拔掉传感器必然卡死”：立即 NACK 等错误可能直接返回，具体触发是等待状态无法完成且需超时退出。

建议：为 ISR 使用独立周期计数的有界驱动或非阻塞采集状态机，并明确失败传播；保持已确认的 TIM6/TIM15 同级约束。验收应注入 SCL/外设等待故障，测量停车延迟与 PWM，不能仅验证正常总线。

## R03：IMU 接收错误仍转换未初始化数据

位置：`BSP/bsp_imu660rb.c:87～94,157～180`。

`ReadRegisters` 忽略发送和接收返回值；`GetAcc/GetGyro` 的局部 `uint8_t dat[6]` 未初始化，随后无条件组装三个 int16 输出。HAL 返回 BUSY/ERROR 或只完成部分接收时，输出可能混入栈残留，而调用方没有有效性标志。

影响：采样器、陀螺校准、角度积分和日志可能把错误数据视为有效测量。当前加速度控制项未启用，不应夸大为所有坏加速度都会直接控制电机；陀螺与日志数据仍受影响。

建议：返回明确状态，只在完整成功后发布帧，定义保留旧值/无效标记及故障处置。仅将数组清零不能解决“把失败当成功”。用 HAL_BUSY、HAL_ERROR 和部分接收替身测试输出保持与状态传播。

## R04：旧 UART 调参缺少跨读取分帧

位置：`App/wireless.c:29～60`，`BSP/bsp_uart.c:76～90`。

`BSP_UART_Read` 只消费当前已经收到的字节；`Wireless_Adjust` 却立即按本次长度解析并清空，没有等待终止字节或保留半帧。

本次将合法命令 `xp100\n` 分成 `xp` 和 `100\n` 两次交付：原 KP=2，预期最终为 1，实际仍为 2。多条命令一次到达也会合并成一个长度不合法的数据块并丢弃。若恰好在四至七字节处截断，还可能把尚未收完的数字末位当作终止字节，提前应用错误数值。

影响：是否成功取决于主循环、LCD 阻塞和串口字节到达时机，不能依赖“一次 PC write 等于一次 MCU read”。

建议：明确既有终止字节契约，持续组帧，按帧解析并保留尾部半帧；分别测试每个拆分点、连续两帧、超长帧及恢复。若需改变历史允许的终止字节语义，先由用户确认。

## R05：停车态空闲风扇配置与物理输出不同步

位置：`App/param.c:356～416`、`App/tuning.c:679～701`；物理风扇 PWM 写入点在 `App/app.c:110,377,540`。

停车 SET_PARAMS 或菜单设置 fan_idle 只修改参数及 Motor 状态，没有同步写 PWM。切档也只分发状态值。停车主循环没有常规刷新风扇输出。

本次起始 PWM=1100，停车设置当前模式/档位 `fan_idle=1200`，收到 APPLIED；状态变为 1200，但 PWM 仍为 1100，保存服务后仍为 1100。

影响：停车配置回显与实际风扇不一致，直到后续运行/停车路径才更新。与 Phase 08 FR-7“停车使用当前档空闲值”不一致。

建议：在明确的停车参数提交/切档位置更新输出，注意只应用当前档，并覆盖 SCB、菜单及停车保存后恢复路径；增加实际 PWM 替身断言。

## R06：UART 速度 PI 修改未同步参数查询的数据源

位置：`App/wireless.c:101～105`、`App/param.c:607～608,659～677`、`App/tuning.c:451～460`。

UART `vp/vi` 直接调用 `PID_SetGain`，而 `GET_PARAMS.values` 经 `Param_GetSpeedGains` 读取 `s_param`。后者通常直到三秒静默保存或显式刷新时才从 PID 同步。

本次发送完整 `vp100\n` 后，活动 KP_v=1，但参数 bank getter 仍返回 20。因此此窗口内 SCB 查询会给出旧 values 与新 effective；客户端若以 values 为基础修改其他项再提交完整八项，可能把速度 PI 恢复成旧值。

建议：统一停车参数修改入口和 RAM 配置所有权，延迟保存仅延迟 Flash，不延迟配置快照；验证 UART→立即 GET_PARAMS→SET_PARAMS 的跨入口流程。

## 其他接口隐患与已知限制

### 两项低优先级接口问题

- `BSP/bsp_uart.c:49`：发送失败返回 `len - TxXferCount`（已发送数量），与 Phase 02 FR-5 的“未发送数量，0 表示成功”契约相反。发送前即超时时可能返回 0。现有主要调用者忽略返回值，故未列为当前主控链高优先级问题。
- `BSP/bsp_w25q64.c:221～245`：读取接口接受 uint32 长度，范围检查允许超过 65535，但传给 HAL 时强制转换为 uint16。65537 会变为 1，可能只读一个字节却返回成功。当前参数和日志调用使用小块，未发现活动调用触发；后续大块读取须分块或明确拒绝超长输入。

### 不应误判为本轮新缺陷的现状

- `gray_calibration.h` 的 32 个值仍为 -1，两种模式拒绝起跑是已确认安全门禁，不能用示例标定绕过。
- 两套传感器始终参与失线保护；只提供电磁信号或只提供白线的环境不是当前双保护验收环境。
- 电磁状态表覆盖普通菜单/串口方向增益及基础速度，属于 Phase 10 已知语义问题。Phase 16 显式调试覆盖只解决指定使用场景，没有完成全局统一。
- 左环岛、跷跷板、路障、增量式 PID 和 IMU 速度积分仍未接入；加速度阻尼输入恒零已有 Phase 05 FR-7 记录。不能未经确认启用这些入口。
- 单参数扇区擦写没有双副本掉电原子性；日志不支持掉电恢复会话。这里作为已有设计边界记录。
- 灰度 700μs、完整控制 900μs、日志持续吞吐、SPI 波形和 AC5 链接仍需实测/工具链验收。日志需持续消化 96000B/s，有限 RAM 只能吸收暂时擦写停顿，不能证明长期平均吞吐达标。
