## 课程介绍

欢迎学习这门与 JetBrains 合作开设的规约驱动开发（Spec-Driven Development，SDD）课程。规约驱动开发目前是配合智能体编程助手构建严肃应用的最佳工作流。你给编程智能体一个 Markdown 文件或一段长提示词，精确说明要构建什么，它就去实现这份规约。你不再手写代码，而是专注于写下智能体本身不具备的上下文信息。

很高兴本课程的讲师是 JetBrains 的开发者布道师 Paul Everett。

（开场小插曲——"等等，我不知道你还戴眼镜。" "对，我其实不需要这个。"）

言归正传，规约驱动开发有三大好处，你马上就能体会到。

**第一**，你可以用对规约的微小改动来控制大规模代码变更。像"使用 SQLite 搭配 Prisma"这样的一句话可能影响数百行代码；把它改成 MongoDB，同样能产生下游的放大效应。这让写规约的效率远高于写代码。

**第二**，规约有助于消除会话之间的上下文衰减（context decay），保住那些不可妥协的关键约定。智能体是无状态的，因此在它启动时立刻加载最高质量的上下文非常重要。

**第三**，规约能提高意图保真度（intent fidelity）。你来定义问题、成功标准、约束条件等等，智能体再据此细化出更完整的计划。

我写规约的一种常见方式，是和一个智能体（比如 Claude Code、Gemini 或 Codex）对话，利用我对各种取舍的理解来做出关键的架构决策，然后让智能体把关键决策总结成一个 Markdown 文件。

写规约需要思考，这是很费劲的工作。你必须决定：想构建什么产品？有哪些功能？采用什么技术架构？如果没有规约，你就等于把这些重要决策交给编程智能体一时兴起的发挥——如果你想快速推进、碰碰运气，这也没问题，但肯定会导致代码更难维护，有时还会做出相当奇怪的产品。

举个例子，我见过一些团队在开发复杂软件产品时没有清晰的规约，结果下游麻烦不断：不同的编程智能体在不同开发者的指挥下快速构建，却各自朝着互相矛盾的方向走。

规约驱动开发的做法是：先在**项目层面**制定一份"宪章"（constitution），定义不可变更的标准；然后通过**功能开发循环**（feature development loops）不断迭代。每个循环把单个功能隔离在自己的分支上，包含规划（plan）、实现（implement）、验证（verify）三个步骤，功能之间留下干净的交接，减少麻烦和上下文切换。

这套工作流同时适用于绿地项目（greenfield，从零开始）和棕地项目（brownfield，已有代码库）。在绿地项目中，你从零开始，通过与智能体对话来制定宪章；在棕地项目中，你基于现有代码库反向生成项目宪章。两种情况下，你随后都会通过功能开发循环迭代，以小步前进的方式管理版本。

在本课程中，你还将学习如何编写自己的**智能体技能**（agent skills）来自动化规约驱动工作流。当然，如果你用一句简短的提示词就能搞定，那也很好——我绝对是"懒人提示法"的支持者，只要它管用。但我认识的优秀开发者，在面对任何有相当复杂度的项目时，几乎总会写详细的规约，因为他们拥有独特的上下文，对"构建什么、如何构建"有自己的见解，这比让缺少这些上下文的模型随机选择要高明得多。

如果你的编程智能体要写 20 到 30 分钟的代码——这可能相当于传统开发者好几个小时的工作量——那你通常最好花三四分钟坐下来，写出真正清晰的指令。

许多人参与了本课程的制作，包括 JetBrains 的 Constantine Chiker 和 Zena Smeova，以及 DeepLearning.AI 的 Isabel Zaro。

## 氛围编程 vs 规约驱动开发

当你听到"AI 编程"，你可能会想到"氛围编程"（vibe coding）。我们来对比一下两者，看看规约驱动开发如何通过把"工程"找回来而获得更好的结果。

氛围编程见效很快：你写一段提示词描述你想要什么，比如"给我创建一个按钮"，然后听天由命。然后你看结果——好大的一个按钮！有点接近了，但在一些重要的地方不对。于是你向智能体指出错误，它再试一次，如此反复，直到你满意为止。最终你会和智能体进行一段很长的对话，而这段历史甚至不会被保存下来。

这种方式对一个按钮还行，但无法扩展到大型的持续性项目。高层次的提示词虽然快，却会产生一次性的代码和不断累积的技术债。

我们需要工程：一份维护良好的规约，一个永久性的技术产物。规约驱动开发是对"无人监督的 AI 生成"这种混乱局面的专业回应。这是一次范式转变：解释"做什么和为什么"的规约，与"怎么做"的实现解耦。

有了规约，我们就得到了一份契约——不仅是人与人之间的，也是人与智能体之间的。你作为人的主要任务现在转变了：学会把你的意图转化为清晰的规约。

规约驱动开发配合智能体编程助手有三大好处：

**第一**，你可以用对规约的小改动控制大规模代码变更。规约中概述应用外观和风格的几句话，可能会转化为数百行 CSS。这种规约驱动的方式降低了与这些超高速编程智能体协作所需的认知负担。

**第二**，规约消除了让多轮智能体会话脱轨的上下文衰减问题。在与编程智能体协作时，它的上下文窗口会被填满，往往导致智能体在"工作记忆"饱和时犯更多错误。规约在会话之间、甚至在不同智能体之间持久存在，把智能体锚定在代码库工作和实现功能所需的核心上下文上。

**第三**，规约提高意图保真度，意味着智能体更有可能产出符合你目标的代码。这是因为规约迫使你在智能体开始生成代码之前，先定义问题、成功标准、约束、用户流程等等。

规约是"氛围编程出一堆垃圾"与"工程化出一个可行的软件产品"之间的关键区别。无论你是从零开始新项目，还是想在一个已运行多年的项目中引入 SDD 方法，规约都能帮助解决漂移（drift）和生产力问题。

打个比方：想想编译器，它把可读的源代码转换成机器码。SDD 则引导智能体和提示词，把规约转换成源代码。更妙的是，规约是用人类语言写成的，便于利益相关者（stakeholders）理解。

规约驱动开发最近作为对生产力担忧的解决方案而兴起：多个 SDD 项目、围绕规约编写构建的工具、关于捕获意图的会议演讲——这些都是更大趋势的一部分，即把软件开发生命周期（SDLC）中的工程经验带到智能体编程中。

规约驱动开发是与**编程智能体**配合使用的，而不是简单的聊天机器人。聊天机器人可以谈论代码，但它访问不了你的项目代码，也访问不了你安装的工具，它只是回应你的提示词。智能体则不同：它们接收你的提示词、制定计划，并借助推理一路自我引导直至得出结果。重要的是，智能体能访问你的代码库和开发工具。

在 SDD 工作流中，我们把这些智能体当作能力极强的结对程序员。它们提供技术知识和速度；而你，作为高级架构师，提供蓝图。随着课程推进，请记住：**智能体是肌肉，规约是大脑**。通过练习，你能确保产出的软件不仅功能正常，而且与你的长期目标保持一致。

## SDD 工作流概览

规约驱动开发会预先告诉智能体如何构建你想要的东西——先是项目层面，然后是每个功能层面，并且越用越好。我们用最高质量的上下文来帮助智能体：先是项目层面的决策，然后是每个功能的细节。这份规约非常详细。

SDD 的一项关键技能是把握**合适的详细程度**。如果你把智能体当作一位能力很强的结对程序员，你通常就能把握好这个度：关于目标、使命、目标用户和约束的上下文要给足；而智能体自己能搞定的低层决策则少管。

这套 SDD 工作流是什么样的？

**第一步：制定宪章（constitution）**。使命是什么？技术栈是什么？路线图是什么？宪章只是把这些项目层面的细节形式化的一种方式。许多开发者用顶层的 `AGENTS.md` 文件来达到这个目的，但项目宪章是智能体无关的（agent-agnostic），而且更结构化。宪章记录了人与智能体之间、同时也是人与人之间的关键决策共识。

- **使命（Mission）**解释"为什么"：项目的愿景、受众、范围等。提前定义这些参数在软件项目中很常见，有助于指导后续的持续决策。
- **技术栈（Tech Stack）**面向工程团队：对开发与部署技术及约束的共同理解。
- **路线图（Roadmap）**是一份活文档，包含一系列阶段，每个阶段用各自的功能规约流程来实现。

宪章起草完成后，我们用一套可重复的流程来处理每个功能：先规划功能，再实现它，最后验证结果。在功能之间，则进入**再规划（replanning）**阶段：修订宪章、更新路线图，甚至改进流程本身。

如前所述，SDD 的一项关键技能是提供恰到好处的详细程度，以创造最高质量的上下文。在功能阶段和再规划阶段，由你来掌舵。

换个角度看：想象你是一名建筑师，把建筑的详细图纸交给施工人员，接下来就交给他们了。你的角色是设计、监督施工，然后验收结果或要求修改。你要避免告诉施工人员怎么干他们本行的工作，而是专注于提供他们不知道的上下文。

规约驱动开发带你从最初的思考走到最终的交付。最棒的是，它让你在那之后还能持续改进。这就是现代开发者开始采用的一种 SDD 工作流。

接下来我们会先看起点：项目宪章。但首先，来做一点准备工作。要获取项目仓库，请按照下一个阅读材料中的说明操作。

## （可选）环境搭建

在发送第一条提示词之前，先聊聊工作区的搭建。如果你已经熟悉在 WebStorm 这类 IDE 中配置 Claude Code 之类的编程智能体，可以跳过这个可选视频。

规约驱动开发是一种不绑定特定 IDE 或编程智能体的最佳实践。你可以选择自己已经在用的配置，或者与本课程相同的配置——VS Code 搭配 Codex CLI、Zed 编辑器搭配本地模型，都很适合规约驱动开发。

由于我们计划开发一个 Web 应用，本课程将使用 WebStorm IDE，搭配 Claude Code 作为编程智能体。两者的下载安装说明已包含在前面的阅读材料中。

让我们打开 WebStorm，新建一个名为 **Agent Clinic** 的项目。这将是一个带 Git 仓库的 TypeScript 项目，便于密切跟踪代码和规约的版本。

虽然包括 WebStorm 在内的许多 IDE 都提供聊天面板，但我们知道大家与编程智能体交互的方式非常多样。在与智能体进行规约驱动开发时，密切跟踪代码版本非常重要。

假设我们想让智能体创建初始提交：每次它需要执行命令时，都会向你请求确认——除非你以不安全模式（unsafe mode）启动 Claude Code。请密切留意 Claude Code 请求你执行的操作，代码的最终责任在你。

在接下来的课程中，你会看到一些在规约驱动开发中使用 Git 的技巧和最佳实践。好，我们的环境就绪了，你的也准备好了。让我们开始吧。

## 编写项目宪章

你需要告诉智能体你的项目情况：使命、受众和其他决策。在本课中，我们将与智能体协作编写宪章。

你的项目到底是什么？假设你在为公司开发一个新的 Web 应用：其开发背后的核心想法是什么？它如何融入公司偏好的技术栈？计划了哪些功能？这三个基础原则构成了宪章——一套全局的高层需求，将指导未来的功能开发，并向利益相关者说明项目的形态。

比如技术栈，你有太多选择。你需要基于合理的取舍和公司的实际使用情况来收窄选项。我们需要把这些写下来——为了智能体、为了队友、为了将来。

但我们不是独自写，而是在与智能体的对话中写。你会惊讶于它能提出多好的问题：你没想到的架构模式、已经能完成工作的现成外部包、或者各种取舍（比如速度 vs 数据保真度）。

使命、技术栈和路线图不只是绿地项目（从零开始的项目）的属性，现有代码库也依赖这三大支柱。几个视频之后我们会讨论如何把 SDD 工作流引入现有项目。

这是本课程贯穿使用的示例项目：我们要写 **Agent Clinic**——一个让 AI 智能体从它们的人类那里"解脱疗养"的地方。Agent Clinic 是对热门教学项目 Pet Clinic 的有趣戏仿。编程智能体们干了很多活，压力山大：幻觉（hallucination）、上下文腐坏（context rot）、内存问题，以及与"同事"子智能体（sub-agent）的协调，都在损害智能体健康。我们来建一家诊所，让它们能就自己的问题获得帮助。

这是一个全栈 Web 应用，后端用 Next.js，前端用 React。应用允许你管理预约、病症（比如幻觉）和治疗方案（比如"上下文输液"）。

我们来看看如何为这样的项目写详细规约。让我们和智能体对话：

首先，把项目描述提供给智能体，并告诉它利益相关者已在 `README.md` 中给出了输入（我们已把它加入仓库）。在重要提示中，我们直接点名了 Claude Code 的 AskUserQuestion（询问用户）工具——这个工具完全可选，我们只是喜欢它在界面中的呈现方式。另外，对于项目宪章，告诉智能体与你一起完成使命、技术栈和路线图。

规约驱动开发最配合"人在回路"（human-in-the-loop）的方式，由你来审查小步变更。所以告诉智能体把路线图组织成小步。

在我们协作过程中，你会看到智能体提出一些非常好的问题（你实际看到的问题可能不同）。第一个问题是："mission.md 应该采用什么语气？"——我选，你猜对了，"俏皮"（playful）。使命部分搞定了。

接下来是技术栈的问题。我们的工程师习惯在后端用 TypeScript，那就把这条加进需求。然后是路线图——它问粒度应该多细，我选第一个选项。

初始访谈完成，点击"提交答案"。智能体会向你请求写入权限，这让变更保持在你的控制之下。如果你接受相应的安全取舍，可以选择"在本会话中批准该命令的所有后续执行"——你会在课程后面看到这个选项。

完成！现在 specs 目录下有了三个文件：`mission.md`、`techstack.md`、`roadmap.md`。

**人在回路时间到，开始审查。** 比如，使命里漏掉了目标受众——这情有可原，智能体怎么会知道你的业务呢？但我们不直接手动编辑，而是继续对话。让所有文档保持一致是更好的做法；让智能体来修改，你自己手动改可能会漏掉相关文档的同步更新。

我们想在这个项目里用 SQLite——因为这是个快速原型，虽然之前没提，但智能体在建议中自己想到了。现在它是我们技术栈的一部分。

最后再做一次全面审查，一开始就把一切都定对很重要。然后把宪章提交（commit），它将成为项目的活文档。

Agent Clinic 现在有了宪章——使命、路线图、技术栈——来指导我们的项目。我们准备好攻克第一个功能了。

## 功能规约：规划阶段

现在我们有了包含各功能的路线图。但怎么构建它们？当然是用规约——从路线图的第一个功能开始。

看一下 Agent Clinic 的路线图，这是我们的第一阶段功能："Hello Hono"。但现在开始写代码还太早，我们需要讨论规约、澄清所有细节。一份好的计划要勾勒出实现方法、工作顺序，以及如何验证成功。

从新鲜的智能体上下文开始。智能体可以从官方来源——宪章——获取它需要的一切。我们将在一个单独的分支上开发这个功能，并向智能体说明。我们的提示词将开启一场关于功能规约的对话：任务计划、需求收集，以及用于验证的记分卡（scorecard）。

智能体会请你做出关键决策。注意潜在的冲突或问题——你不必同意智能体提出的方案，有任何让你不安的地方都要澄清。

- 关于第一阶段范围：就按写的来，保持不变。
- 关于需求：锁定 Hono 版本，并强制严格 TypeScript。
- 关于确认方式：手动 curl 就行。

然后提交。

真快——肯定是因为"nano"（极小的）嘛。工作完成，球回到我们这边：审查智能体创建的功能规约。先审查功能计划。一开始就把这些文档定对非常重要，能让智能体保持在正轨上。如果发现问题，让智能体去修，确保它保持需求和验证文档的同步。

比如，我们希望在第一个功能规约里有一个好看的占位主页——通过智能体来做这个修改。接着看需求文档，它也更新以反映主页改动。这里是指明任何重要技术需求或约束的正确位置。别匆匆略过，但也别写变量名这类细枝末节的技术细节——我们要控制过程，但不要过度微操智能体。

最后看验证文档：确保智能体能检查自己是否做对了——同样已为主页更新。

功能规约完成。在 IDE 里创建一个提交。

回顾一下我们做了什么：制定了功能规约策略、建了功能分支、与智能体访谈"这个功能该做什么"、把结果写进 Markdown 文档、审查规约文件、提交。你在规约里做的修改会向下游放大成数百行代码，所以花在这里的时间很值。

## 实现阶段

到了实现环节。我们正在处理项目路线图中第一个功能的计划，功能规约已完成，现在做完整实现。

先快速回顾一下这个功能规约的计划——这就是第一个功能"Hello Hono"，功能规约文档里有我们需要的一切。

开始实现前，用 `/clear` 命令清空上下文。然后回到智能体，输入提示词让它实现所有任务组。有时你也可以选择一次只实现一个任务组，步子和提交更小——这个技巧在小错误会向后累积的领域尤其有用，比如安全或数据库管理。

Claude 运行时，你可以观察控制台显示的变更，实时查看进度。之后，我们可以在提交窗口查看最终变更并逐个检查——这让我们能抢先一步审查工作。这正是开发者在这种范式下的关键角色：作为架构师或监督者，确保智能体拿到了一份清晰的契约。

我们还能看到工作总结：智能体为每个任务组提供了执行工作的额外细节。

现在去 `package.json`，运行应用。服务器在控制台启动，浏览器显示这个功能规约的成果——没多少东西，我们说了"nano"嘛，但能看到屏幕上有像素了，感觉不错。

我们刚实现了一个功能，智能体做了它的验证。下一课，轮到我们做验证了。

## 验证阶段（人工审查）

功能就绪固然好，但先别合并（merge）。在这最后一步，我们与智能体协作审查工作。好在程序员早有趁手的验证工具——毕竟程序员长期以来每周都要花好几个小时做代码评审。

从提交视图开始，逐个过一遍变更。把你的审查重点放在高层问题上——功能是否可用、是否体现规约——而不是"用了哪些 CSS 类"这类细节。

比如 `home.tsx` 太简陋了——"nano"也太 nano 了。我们想要一个带清晰地标（header、main、footer）的布局组件，拆成子组件，还要建一个 CSS 文件。

结果发现，代码里的这个错误源于计划里的一个错误——我们没提这个要求。让智能体修复，从而同时修正规约和实现。

这种"智能体生成、我们验证"的过程就是所谓"人在回路"。因为智能体写代码极快，软件开发者们最近在谈论**认知债务**（cognitive debt）——追踪你的代码在做什么、如何演进所带来的心智负担。这就是为什么为了让这个过程又快又好控制、减少认知债务，变更必须保持可管理的规模。

智能体在做我们的修改，同时也在验证这些修改没有破坏任何东西。

好消息：智能体完成了，并给出了简要总结。功能计划新增了第五组任务来列出这些新步骤；代码里有了布局组件，还加了 CSS 文件。

看起来三个子组件被放在了同一个文件里，但这不符合惯例。我们用 IDE 的移动（Move）工具把它们各自放到单独文件里——这类改动在编辑器里很容易，我们一向擅长，不需要智能体，对吧？自己动手就行。

且慢——这会导致"漂移"：其他文档（规约、README）会不同步。让智能体修正所有相关引用，免得以后浪费时间。

全部修改完成。有没有弄坏什么？测试能帮忙，但智能体没装我们的测试包。既然所有功能都需要测试，我们下一课来讲。

现在我们准备好把这项工作标记为完成并合并结果。注意，宪章的一部分是随这个功能在同一个分支上更新的。规约的版本管理、以及把规约与代码变更关联起来，在社区里仍是个演进中的话题。路线图的改动很小——只是勾掉路线图上的一个步骤，所以把这些更新放在同一分支没问题。如果宪章整体更新比较复杂，最好放到单独的分支。

我们刚刚用规约驱动开发完成并验证了第一个功能。但等等，是不是该再看一眼项目的大局？

## 再规划（Replanning）

第一个功能成功实现了，迫不及待想再来一次、再来一次。别急，退一步，做点再规划——**欲速则不达**。

我们的工作流里有个验证环节，测试有利于验证，但我们没告诉智能体我们的测试偏好。开一个再规划分支，更新宪章中的技术栈。

如上一视频所见，规约版本管理是个演进中的话题。宪章是活文档，最好在单独分支中更新它，这样能跟踪哪个版本的宪章产出了哪些代码。我们用一段提示词来陈述我们的测试策略。

看起来智能体只更新了 `package.json` 加了个脚本，没加依赖——等以后真正跑测试时注意这一点。这个"添加测试框架"的变更适用于未来的代码，但我们再告诉智能体：基于这次宪章变更，更新现有的功能规约和实现。

这两段提示词之后，有了不错的改动。智能体搭好了测试框架但没写测试本身——让智能体写一些新测试。

有了这个配置，我们可以在编辑器里方便地运行测试。在调试器下运行，让我们有机会作为"人在回路"逐步跟踪代码执行。看起来不错。现在验证环节有了测试，提交吧。

有时我们会意识到产品计划需要调整。比如实现第一个功能后，产品经理发来更新：40% 的用户在移动端，我们要强调响应式设计（responsive design）。告诉智能体：我们要响应式设计，并修正产品规约和功能规约以及相关代码。

由于开发还处于很早期，这次更新是小改动，直接在再规划阶段实现是合理的。但如果新工作量很大，最好作为独立的功能阶段排进路线图，而不是直接在再规划里做掉——用你的判断力。记住，我们希望规约捕获的是**决策**，而不仅仅是代码；要尽量保持两者同步，以利于团队沟通。

智能体已实现我们的响应式修复，不仅改了代码，还更新了产品规约和功能规约。轮到我们审查变更了——过一遍 diff。看起来不错，提交。记住：小步工作、频繁提交，能让审查不至于压垮你的大脑。

再规划的前半部分搞定，接下来退一步做点项目"内务"。比如重新审视项目路线图，看下一个任务是否仍然合理。路线图显示的下一个功能我们下一课会讲——它还是正确的选择吗？通读路线图，功能二、三、四、五有点抱团，我们把路线图更新为一步搞定它们。提交，稍后开始做这项新功能。

再规划可以是关于一个功能或整个项目的，也可以是关于**跨项目、跨组织地改进你的规约驱动开发工作流本身**。

举个例子：假设你有几位非技术背景的利益相关者想跟踪项目进展，你希望每次合并到主分支时自动更新变更日志（changelog）。大多数 AI 编程智能体支持**技能**（skills）——一个指令与资源的包，为智能体提供新能力和专业知识。技能非常适合定义明确、可重复且需要项目或组织特定上下文的工作流——用一个技能来实现变更日志更新再合适不过。

你可以手写这个技能，但很多智能体其实自带"帮你写技能的技能"。让智能体帮我们写并维护一个变更日志技能。智能体开始干活。

有一点需要我们考虑：这个技能是本项目独有，还是该成为所有项目的标配？这是个风格选择，用着用着你会有更深的体会。你会学会用技能自动化你的 SDD 工作流——比如你的验证环节可能包含更新 README、lint、格式化、跑测试等质量检查，可以和智能体合作把它们打包成一个"验证技能"。流程可重复，手工活更少。

智能体完成了。滚动窗口看看它建了什么、怎么用。注意它选择建在**全局技能区**——这个技能现在可以跨所有项目使用。另外，Claude Code 用新技能在本项目生成了变更日志。变更日志是你与利益相关者（包括智能体）沟通的方式，打开手动审查一下——看起来不错。

再规划工作完成，提交收尾，合并分支。

现在，你作为开发者的大部分工作是规划和验证而非实现，那就在功能之间专门留出再规划的时间。下个视频我们做另一个路线图功能。宪章升级了，工作流也升级了，我们在不断进步。

## 第二个功能：Agents 与 Ailments

在继续下一个路线图功能之前，先讲几个应对常见痛点的策略——**AI 疲劳**（AI fatigue）。智能体一次能生成大量代码、大量变更，海量代码让"人在回路"的验证工作令人精疲力尽——要审查的太多了。

要对抗这种混乱，确保每个功能阶段之间有干净的分界。每个功能开始时我们都应该处于正确的心流状态：我还有未完成的工作吗？上一个功能分支合并到 main 了吗？下一个路线图条目还是正确的事吗？清空智能体的上下文了吗——确保规约捕获的是**意图**而不是记忆残影，也让它把有限的上下文预算集中到下一份工作上？

花点时间好好开始，才能好好完成。这些我们都做了。清空上下文，开始下一个功能：**Agents and Ailments（智能体与病症）**。

顺便说，我们一直在重复输入同样的东西——以后的课程会讲怎么把这种重复提示精简成自定义工作流。

和之前一样，智能体提出了好问题。第一个问题是这些功能是否放在同一个阶段——上一课我们已经决定一起做，所以选"是"。数据库迁移选纯 SQL（plain SQL）。验证选项选一、二、三。提交。

智能体起草规约时，我们能看到它的一些选择。观察智能体的推理过程很有用——如果你的智能体有详细模式（verbose mode），还能更深入地看到它的中间想法。

看起来不错，但我们要做一个小改动来捕获我们的意图：我们想用 Pico CSS 作为 CSS 框架。接着审查功能规约的三个文件，从需求开始——让智能体修改需求，并确保其他文件同步反映改动。工作完成后提交功能规约，这次让智能体自己拟提交信息。

第二个功能的规约就绪，进入实现阶段。规划阶段与功能阶段的分界能避免上下文溢出——我们的和智能体的。如果功能太大无法一次实现完，让智能体先实现功能计划的一部分，把变更规模保持在可管理范围内。

智能体已实现第二阶段功能。我们观察了过程，对所做工作有个大概了解，但这还不够。慢下来，动脑子——深入审查变更。

每个人对"审查多少"有自己的风格。要发挥智能体的长处并减少 AI 疲劳，就抓住高层需求，别纠结变量名之类的琐事——只要确保这代码是你敢署自己名字提交的就行。

比如，它给 props 用了内联类型标注，我们希望 prop 定义抽成独立的 TypeScript 类型——让智能体在代码各处统一修复。这个决定你之前多半没写进规约。记住，像"抽离 prop 类型"这样的遗漏不是失败——你在发现新细节的过程中演进规约，把它捕获下来会让未来的结果更好。

审查完毕，这又是小步提交的好时机。

最后一步：验证。看看智能体在这个功能规约里为验证环节计划了什么——不错，执行我们的验证。记住，我们要通过运行应用来确认改动是好的；同时为了防止认知债务，还要验证我们**理解**这些改动。测试是梳理流程的好地方：读一些测试，在调试器下运行，边跑边探索。

有时你需要验证自己有没有被"骗"：让智能体派出几个子智能体，对整个项目连同这次功能变更做一次深度评审。深度评审给智能体更多思考空间，用子智能体还能保护主智能体的上下文窗口不被污染。子智能体会带回一些问题和建议——都不错，那就动手。智能体一阵忙活、修了一堆问题、跑了测试，把项目带回了良好状态。把这一招收进你的工具箱：**第二遍检查时，智能体通常能发现重要问题。**

验证完成，功能完工。提交本次功能工作。最后一步，用上我们之前做的变更日志技能——功能分支上的变更已记录成文档。再提交一次，然后合并分支。

之前的课程讲过功能之间的再规划，这里做个快速版：看一眼路线图，下一个功能还合理吗？不错。项目状态良好，准备好迎接下一个功能。功能之间这种干净的断裂有助于对抗 AI 疲劳——现在你可以去喝杯咖啡了。

我们开始看到一个可重复的 SDD 功能开发流程，一个能捕获决策的流程。下一步，检验这个假设：我们的积累够不够构建一个 MVP？

## MVP 冲刺

进展很大：两个功能用规约工作流实现了。但管理层当然来提了要求——要个 MVP（最小可行产品）。我们的进度够不够做一次试验？

用标准功能规约提示词的一个变体：这次告诉它实现路线图的剩余部分，并就现有功能规约给些指引。

一般来说，只有当你对宪章和规约的质量有信心时，才该一次实现这么大的块。你给智能体的上下文越好，结果与你的意图对齐的把握就越大——而且你得确保自己扛得住审查和验证的量。

但既然冒了这个险，现在就把 MVP 当作对我们的宪章和已完成规约的一次极限测试：如果结果和我们想要的不一样，说明我们需要非常负责地再来一轮再规划，消除任何把智能体带偏的因素。

智能体又问了我一些问题——又是好问题和好建议。很多规约文件一开始都是与智能体的来回对话。访谈完成，点击提交，让 MVP 规约落盘。

审查规约总是值得的——你常会注意到智能体为填补空白做出的错误假设。快速过一遍计划、需求和验证。照例小步快走、频繁提交：保存规划阶段的规约。

规划完成，该让智能体做一大步实现了。智能体开始大量工作。完成后——见证时刻：运行 MVP。每个版块现在都由数据库查询出的示例数据驱动，内容充实多了。

通常这时该验证代码结果了，但这是 MVP——让智能体**验证规约**。事实证明这很有用：智能体指出了 MVP 暴露出的规划漏洞。我们可以把这份评估分享给利益相关者做 MVP 评审，然后合并或归档分支。

我们的规约驱动工作流成功了：一份宪章加两个功能之后，MVP 在我们的引导下产出了可用的演示。

## 棕地项目：把 SDD 引入遗留代码库

当然不是所有软件项目都要构建 MVP，很多项目是所谓"棕地"——从现有代码库开始。人们说规约驱动开发、甚至 AI 本身只适合绿地项目，但 SDD 对现有遗留项目同样有效。本课我们把 SDD 引入一个现有项目。

为方便起见，我们用你已经熟悉的项目：Agent Clinic 的 MVP。通过在 main 分支上移除 specs 文件夹、在一个新的 Claude Code 会话和新目录中打开，我们把它"变成"遗留项目。

项目背景在 `README.md` 里，待办工作列在 `todo.md` 里。你的真实遗留项目可能有完整的产品计划，散落在 issue 跟踪器、电子表格、Word 文档等等地方。

还记得我们的流程吗？从宪章开始。用几乎和第 4 课相同的提示词，这次告诉它从现有文档里找路线图条目——这里是 todo 文件。记住，智能体会探索并在某种意义上**逆向工程**出现有代码库的 SDD 文档。宪章将帮助智能体未来的代码变更与过去开发者已创建的东西保持一致。

如果你有更多上下文，随时可以补充——比如你被空降到这个项目，是要在实现呼声很高的功能的同时提升效率。流程相同，但对话可能更丰富，因为智能体有更多材料：代码、提交、文档等。

你会看到这里出现大量工具调用，智能体在探索代码库。看看为遗留项目生成的宪章：使命里有受众、项目构想和补充信息；技术栈里 Claude 提取了项目文件结构、框架版本，以及向我们澄清的问题；路线图里的工作按阶段组织，与 todo 文件对应。

为产出的宪章文件创建提交，并附上提交信息——记住，在 SDD 中，规约是版本管理策略的一部分。

我们的遗留项目现在有了 SDD 地基。从今往后，工作流与前面课程讲的完全一样：先从路线图取下一个功能，与智能体对话规划。我们要做第一阶段——反馈表单（feedback form）。

很好，分支和这个功能的规约都有了。审查功能规约：计划、需求、验证。然后提交功能规约。与智能体对话修正后，着手实现。智能体完成后，我们做验证，确保代码没问题、功能符合预期。

功能循环完成，提交并合并分支。

现在该再规划了——一定要给它留时间。既然刚把 SDD 引入项目，你可能会发现很多东西要调。这样，我们没费多少手工功夫，就把一个遗留项目迁移到了规约驱动开发之上：流程有据可查、按步推进、有工程章法、掌控在自己手里。**规约现在就是项目的记忆。**

## 用技能自动化你的工作流

你已掌握 SDD 工作流，想要更快、更轻量的东西？本课我们做自动化——但是按我们自己的方式，用自定义流程。

前面讲过智能体技能——一个为智能体赋予新能力和专业知识的开放标准。比如，每次启动功能规约我们都重复输入同样的提示词：做这个、做那个、写这三个文件。用技能来自动化它，并让智能体帮忙写这个技能。

让智能体用它的"技能创建器"（skill creator）跟我们谈清楚。顺带一提，社区里有很多这类"技能之技能"（skill skills），你也可以安装现成的。

智能体运行时可能会问后续问题，通常都很到位。访谈完成后提交回答，智能体继续。在它构建技能期间，盯着输出——它做的选择是你想要的吗？

如你所见，智能体把技能写到了这个目录。注意，技能可以是项目级的，也可以是全局的。

技能有几种调用方式：在提示词里先提技能名再说要做什么；也可以让智能体从一个技能里调用另一个技能。按照技能的开放标准，智能体根据技能描述来决定何时调用它，这个过程叫**渐进式披露**（progressive disclosure）。但它的判断并不总是完美——尤其当上下文窗口变大时。用和文件标记（file tagging）同样的经验法则：**你明确知道要用某个技能，就点名它**，这样能省下思考用的 token。

智能体有内置的斜杠命令，比如 `/clear`。斜杠命令起初很流行，但很多智能体正从自定义斜杠命令转向技能。

有时你需要给智能体更多资源，比如访问某个 API、私有知识库、数据库等。到目前为止，扩展智能体的通用方式是 **MCP（模型上下文协议，Model Context Protocol）**。比如，智能体需要关于软件包的最新优质上下文，最流行的选择是 Context7——一个把软件包最新文档带进智能体上下文的 MCP。这样你的智能体就能跟上 React 9.2 及以上，而不是停留在 React 9.0。

MCP 服务器仍然流行，但**用 CLI（命令行）工具的技能往往能用更优雅的方式达成同样目的**——Context7 现在就是这么建议的：一个调用 Context7 CLI 工具的技能。

我们来给 Claude Code 安装 Context7 包。安装过程中立刻就能看到选择：MCP 服务器还是"CLI + 技能"——选后者。第一次用需要注册账号（我们已经注册并登录了）。完成后回到 Claude Code，用一个调用 Context7 的示例提示词试试。

智能体运行时，我们看到它检测到需要使用 Context7；完成后，它显示现在已经知道如何查询我们技术栈的信息了。从 MCP 服务器转向"技能 + CLI"的趋势正在加速——人们在重新思考 MCP，因为 CLI 工具能以更少的配置、更少的上下文占用采取行动。

随着你的工作流实现（技能等）不断扩展，你会想分享它们：给自己跨机器用、给队友用、也许给外界用。有些智能体（如 Claude Code）有**插件**（plugins）——一组可安装、可更新的智能体扩展。免费插件的社区正在壮大，去看看有没有能提升你 SDD 生产力的。记住，插件还不是跨智能体标准；和应用或依赖一样，插件能执行代码，所以安装和更新时要确认你信任它。

GitHub 的 **Spec Kit** 是把规约驱动开发工作流配合智能体正式化的一次尝试。为项目安装 Spec Kit 后，你会在智能体里获得类似本课程工作流的斜杠命令：`/specify`、`/constitution`、`/plan`、`/tasks`、`/implement`。

另一个流行的替代方案是 Fission AI 的 **OpenSpec**：它遵循类似的"提议（propose）—探索（explore）—应用（apply）—归档（archive）"工作流，其中"提议+探索"对应规划步骤，"应用"对应实现，"归档"对应再规划。它还有快速功能的范式模板。这两个包都带有分支管理、验证脚本和有主见的规约文档格式等实用特性。我鼓励你试验这些开源工作流，来打磨你自己的流程。

有时做到一半你灵光一现：想跟智能体研究一下，但又不想打断分支上的工作——比如数据库选型，但你还没打算采纳这个想法，不想把它放进路线图。对话产生了不错的想法和问题，我们接受大部分建议，但对其中一个改了主意。你不想丢掉这些成果——让智能体把研究报告写到固定位置，留作**研究 backlog**。这个文件记录了你的对话与结论，之后你可以让智能体把这项研究排进路线图，并附上 backlog 文件的链接。等它越积越多，你可以写个技能把研究流程自动化。

规约驱动开发让智能体按你的方式写代码。你可以采纳现有的 SDD 框架或工具，再用技能按你团队的方式定制它、运营你的项目。

## 标准化与跨智能体迁移

规约驱动开发把工作从"怎么做"移到了"做什么、为什么做"。智能体和模型进步飞快，你不想让自己的工作流绑死在单一选择上。本课看标准如何让我们**换智能体而保留工作流甚至工具**。

以下智能体标准有助于这个目标：**MCP** 用于外部工具，**AGENTS.md** 用于规则，**Agent Skills** 用于捕获带额外上下文的可重复工作流，**ACP（Agent Client Protocol，代理客户端协议）** 用于连接智能体与客户端。

以 OpenAI 的领先 AI 智能体 Codex 为例：它既能跑在桌面应用和编辑器里，也能跑在终端里。看看实战：把第 12 课的功能规约技能复制到 Codex（它把技能存在不同的路径），迁移后运行良好。这让你可以在同一项目里在智能体之间来回切换，保住你的 SDD 工作流。

我们还能借助 ACP 标准，在不同编辑器里用不同的智能体。ACP 让智能体与编辑器的连接变得简单——如果你的智能体和客户端都支持 ACP，就是绝配。

为了让这种即插即用更简单，**ACP 注册表**（ACP Registry）把"在客户端内发现、安装、连接智能体"自动化了，覆盖整个生命周期，让混搭更容易。

比如在 JetBrains IDE 中，AI 聊天窗口就能引导你从 ACP 注册表安装，IDE 随后会列出兼容的智能体。OpenCode 是流行的开源智能体，ACP 注册表让它很容易加入 IDE——点"安装"，它会自动完成 OpenCode 本身的安装（如需要，很贴心）以及与 IDE 的集成。完成后，你的 IDE 就原生集成了新智能体，可以在同一编辑器里与其他智能体并肩使用，作为 SDD 的一部分。

这些新的智能体标准带来了新可能，但它们实际如何工作？ACP 架构就是为"把智能体和客户端插到一起"而设计的——事实上，它的协议与 LSP（语言服务器协议）所用的一致。ACP 的覆盖范围超乎想象，比如编辑器里的"下一处编辑建议"（next edit suggestion）和计划模式（plan mode）。更进一步，用 ACP 你还可以写自己的自定义智能体，装在本地工具里。

选哪个智能体？行业变化很快，评测网站纷纷涌现，排行榜给出各种评估。当然，排行榜变得也快，所以保持关注，并基于对你重要的标准做决定。我们的规约工作在更高的层次，不绑定任何单一智能体或 IDE。这节课证明了：**我们的工作流和工具是为智能体无关性而构建的**。随着更多标准出现，这种灵活性只会增强。

## 结语

恭喜你完成本课程！你已经看到如何从氛围编程——祈祷智能体按你想的做——走向规约驱动开发——更接近你真正需要的东西。你写过宪章、通过对话规划功能、以人在回路的方式验证、用技能和标准自动化工作流。

**你今天写下的规约，就是项目明天的记忆。** 保持它们锋利，持续改进你的流程。记住：**最好的代码始于出色的规约**。

你和我认识的许多工程师一样，可能都见过步子迈得太快的后果。让我们把工程找回来，让你继续做自己软件的掌舵人。

我真心在乎在所有事情中寻找快乐和意义，也很期待看到你用这些做出什么。放轻松（take it sleazy），去做点酷东西吧。
