## 1. 设计理念与原则

本体系源自规约驱动开发（SDD）方法论，核心思想是：**前层治理约束开发，Phase 保存完整阶段设计与验收，Docs 与代码表达同一固件的功能和实现语义**。

```text
mission / techstack / roadmap / code-style / AGENTS：目标、约束、排期与执行规则
                         ↓ 约束
Phase：背景、需求、详细设计、决定、计划、文件/符号映射、验收标准与实际结果
                         ↓ 落实
Docs ⇄ 代码：当前功能、算法、参数、状态、时序、错误与兼容的说明和实现
```

读者路径：**目标与约束 → 阶段完整设计 → 当前整体说明 → 源码**。参数经 `Docs/parameters.md` 反查，模块经 `Docs/architecture.md` 反查。互译是语义对应，不要求逐行翻译或自动生成代码。

### 1.1 八条核心原则

1. **规约先行**：新增、修复、重构、删除代码或修改工程配置前，先在 Phase 明确完整需求、设计、文件/符号映射、验收和 Docs 目标草案，消除未决设计并独立提交；本组开工先更新 Docs，紧接代码，核对一致后同批交付。机械改名同样适用；只读调查与不修改仓库的构建取证可按项目规则直接进行。
2. **职责唯一**：Phase 完整保存该次背景、需求、详细设计、决定、计划、文件/符号映射、验证标准和实际结果，按阶段基线解释；Docs 保存当前功能和实现说明。不能为避免重复而删除 Phase 设计正文。
3. **人在回路**：影响外部行为、接口、安全、兼容性、实时性、参数或休眠代码处置的未决事项必须由用户决定。已明确授权的常规编辑、核对和提交按项目规则推进，不对每个步骤重复索取许可。
4. **语义对应**：一个功能有一个稳定 ID 和唯一主说明条目；协作实现可以涉及多个文件，辅助函数归入所属功能，不机械要求每个 C/H 单独建立 Markdown。
5. **小步提交**：按可审查的任务组推进。Phase 确认并提交 → 先更新本组 Docs → 紧接实现 → 双向核对 → 匹配 Docs 与代码同批交付。未开工组目标继续留在 Phase。
6. **同步维护**：无论人工还是智能体修改，都要核对相关 Phase、Docs、入口及索引。目录改名、移动或接口变化必须修复引用，避免文档漂移。
7. **事实与目标分开**：当前实现、已批准目标、待决定方案和历史结果分别标记。描述实现不代表批准其行为；源码存在不代表硬件通过，测试通过不代表所有风险已消除。
8. **工具无关**：正文采用 Markdown，不绑定某一智能体或问答工具。JSON、日志、图片和构建产物可以作为证据或辅助索引，但不替代可读功能契约。

### 1.2 文档角色与治理关系

前层治理文档 → Phase → Docs ⇄ 代码覆盖需求、设计、实施与验收。每个 Phase 须指出适用使命目标、技术红线、阶段依赖和代码标准；辅助资料提供依据，不替代正文。

| 角色 | 内容 | 生命周期 | 唯一维护位置 |
|---|---|---|---|
| **项目治理** | 使命、技术约束、代码标准、路线图、协作步骤 | 长期维护 | `specs/mission.md`、`techstack.md`、`code-style.md`、`roadmap.md`、`AGENTS.md` 各司其职 |
| **阶段层（Phase）** | 背景、FR/TC、详细设计、决定、计划/依赖/风险、映射、验收标准及实际结果 | 阶段结束后完整保留 | `specs/features/NN-<name>/` |
| **现行功能层（Docs）** | 功能契约、接口/格式、状态/时序、代码定位、验证方法及限制 | 跨阶段持续演进 | `Docs/` 的唯一功能主条目 |
| **辅助层** | README、变更日志、研究、专项报告和原始证据 | 按用途维护或冻结 | 对应入口、`specs/research/`、报告目录及证据文件 |

权威按问题划分：查“为什么改、本次如何设计、修改哪些符号、谁决定及如何验收”看 Phase；查“当前功能如何工作、哪里实现、如何验证”看 Docs；查实际执行语句看代码。若三者冲突，登记冲突并确认目标，不能自动选择旧文档或当前代码作为新的设计决定。

### 1.3 相对原版的主要变化

| 原版安排 | 2.0 安排 |
|---|---|
| 功能三件套承载主要功能说明 | Phase 保留完整开发单元，新增 Docs 说明当前功能及实现 |
| 功能规约与代码直接关联 | Phase/FR → Docs 条目 → 实现与验证，支持模块反查 |
| `specs/` 是主要阅读中心 | `specs/` 管治理和阶段，`Docs/` 是现行功能入口 |

| 每组默认运行自动化验证 | 强制审查与适用构建保留，其他验证按影响选择，纯文档只核对文档 |

## 2. 目录结构

标准目录相对于**受本体系治理的项目根目录**，不必等于 Git 仓库根目录。

### 2.1 命名规则

- 阶段目录为 `NN-<kebab-case-name>`，NN 与 roadmap 的阶段身份对应；阶段增多时可扩展位数，但不得借排序改掉已有编号。
- 功能 ID 独立于 Phase 编号。示例：`F02` 是起停功能，`P12 FR-2` 是某次阶段需求，二者不是一对一关系。
- 主条目使用显式稳定锚点，如 `<a id="f02"></a>`；必要时细分 `f02-start`、`f02-stop`。标题改写不应改变这些锚点。
- 可按维护领域增加阶段分组，但分组不是新身份。调整路径必须同步相对链接、索引和入口，并记录迁移。
- `Docs/` 的 D 必须大写。其内部文件和领域目录通常使用小写英文加连字符；`AGENTS.md`、`README.md`、`CHANGELOG.md` 保留固定名称。
- 研究记录使用 `YYYY-MM-DD-<topic>.md`。既有中文资料名和用户指定交付名可以保留，不为“统一命名”擅自重命名历史资料。
- 仓库内链接优先使用相对路径和稳定锚点；聊天交付链接可使用文件绝对路径。代码行号只作辅助，关键定位使用真实文件和符号。

### 2.3 SmartCar 的分类、粒度与兼容契约

#### 2.3.1 分类依据与当前问题

现有分类总体沿用固件职责，保留七个领域目录，不按 Phase、源码文件数量或缺陷编号重新分组。本次分类规则针对领域内主题粒度和跨域边界：F26把ADC/编码器/PWM混在一起，F29把时钟/DMA/多种器件驱动混在一起，F08把多种控制器和电机执行混在一起；另一边UART、DL1B又是单项。结果是读者能找到大概位置，却仍需在压缩段落和源码中自行还原完整功能。

分类分为四个层次，不能把它们混成同一个编号体系：

| 层次 | 分类依据 | 约束 |
|---|---|---|
| 领域目录 | 固件的稳定职责与抽象层次 | 保留system/sensing/control/services/hmi/platform/guides，不随阶段或源码搬迁而改名 |
| 主题页 | 能独立理解和修改的一项功能、机制或完整操作场景 | 同页内容应共享主要数据流、状态/参数和验收目标；不按每个C/H机械拆页 |
| F编号及子条目 | 稳定的功能身份与细分定位 | 保留F01～F33；拆细旧功能时增加子锚点，不把目录、页数和F编号绑定 |
| 源码映射 | 实际实现位置和协作关系 | 一个主题可对应多个模块，一个模块可参与多主题；实现和状态的详细说明各有明确主归属 |

主题拆分条件：存在独立输入输出、主要状态或配置、错误语义及验证目标，且读者会单独查阅或修改。满足这些条件就拆页；只是一组共享算法的小型getter、薄转发或私有辅助函数则留在主题内部。页长仅是阅读提示，不作为硬性拆分阈值。

#### 2.3.2 七类职责边界

| 目录 | 主说明范围 | 跨域内容如何连接 |
|---|---|---|
| `system/` | 启动、生命周期、运行调度、模式切换、停车及安全编排 | 描述何时调用感知/控制/服务，不重复算法公式或外设寄存器流程 |
| `sensing/` | 将原码转换为业务观测量：电感偏差、灰度标定/质心、姿态、滤波等 | 原码采集、通道/rank/引脚和驱动返回语义链接platform；保护动作链接system |
| `control/` | 观测到控制意图/执行值：控制器、双模式协调、状态配置、元素与休眠控制 | 说明业务PWM/方向/里程语义；物理输出、CCR和极性实现链接platform |
| `services/` | 参数、持久化、日志、通信、上传及导出等业务服务 | 日志格式/会话/导出状态归日志主题；帧封装/ACK/可靠传输归通信主题；SPI物理/DMA驱动归platform |
| `hmi/` | 用户操作、页面、按键分发、显示与编辑流程 | 按键电气采集归platform；参数实际生效/保存归services；不能因有菜单就把业务规则放到HMI |
| `platform/` | 板级资源、驱动、原始采集与执行、时钟/DMA、共享总线、独立板测机制 | 正常业务算法链接sensing/control；板测操作步骤可由guides引用机制，不复制实现细节 |
| `guides/` | 构建、烧录、配置切换、验证工具和证据维护方法 | 引用AGENTS/code-style的现行政策和Phase的本次验收；不另创一套治理规则 |

跨域功能按“主要机制在哪里”确定主说明；从其他领域保留协作链接。例如灰度原始完整帧发布归platform，标定和质心归sensing，失线后停车归system，不能把三者当成三份相互竞争的灰度算法说明。

#### 2.3.4 功能身份、主归属与旧链接兼容

1. 保留F01～F33身份；F26、F29这类宽功能保留父级总览，细节用上述稳定子锚点表达。拆页本身不新增F34，也不重编号旧功能。
2. F父条目负责功能范围、子功能和协作总览；子主题负责自己的算法、状态、参数、错误及源码定位。父页引用子页，不复制成另一套完整说明。
3. `traceability.md`增加“父功能/具体子条目/主说明/源码主归属”字段。一个FR指向其实际涉及的子条目，确实跨域时列多个，不把父级总览当作所有需求的唯一终点。

5. 旧文件保留现存显式锚点和已有被引用的章节入口，注明详细内容的新位置。主要导航切换到新页；旧链接仍能到达明确的对应内容，不仅跳到新的总首页。
6. Phase历史正文和原始证据中的路径不批量改写；现行导航、可复制模板及必要承接说明更新到新主条目，保留当时基线含义。
7. 文件移动不改变F身份；以后新增实际功能才建立新的F身份。一个新Phase可以修改多个旧F，一个F也可由多个Phase演进，不建立Phase号与F号一一对应关系。

#### 2.3.5 全局阅读入口

- `index.md`提供按领域的能力总览及推荐阅读顺序，说明正常模式、测试模式、启用/休眠与限制；不能只给一串文件链接。
- `architecture.md`提供整体启动/运行/停车数据流、依赖和模块反查；目录结构不能替代运行链说明。
- `traceability.md`提供前层约束/Phase需求到功能父项及子项的追溯；阶段完整设计继续在Phase。
- `parameters.md`提供按采集、控制、保护、存储、通信、HMI及板测分类的参数反查。链接须指向主主题的具体参数表，而不是宽泛父页。
- `known-issues.md`提供当前实际缺陷与待验限制，回链受影响主主题和阶段；缺陷编号不作为功能目录分类依据。

#### 2.3.6 分类迁移步骤

先登记旧页/旧锚点→新主题/新锚点的清单，再在当前样板中落实F08/F12和F33粒度；样板核对通过后，完成平台与感知拆页、参数/临时调参分离，最后统一全局索引和兼容入口。每批正文迁移与相关链接调整一并完成；不先删旧页等待后续补链，不借分类迁移重写算法或验证历史。

- 参数和记录格式写明版本、字节布局、单位、校验覆盖及兼容策略；多个传输入口复用同一布局时交叉引用。
- 重要函数与协作调用链可定位；辅助函数可集中列在模块主功能页。协作页引用主说明，不复制完整符号表。
- 休眠、规划、仅观察、未接入或条件编译功能必须注明，不混入现行可用能力。
- 纯粹补录现状、尚无独立 FR 的边界功能可明确注明来源与需求缺口；未来行为改变先补 Phase，不能虚构既有授权。

### 4.5 三段追溯与维护位置

**第一段：治理 → Phase**：Phase 背景与约束说明本次使命目标、适用技术红线、路线图依赖与代码标准检查。

**第二段：Phase → Docs**，唯一全局索引为 `Docs/traceability.md`；阶段正文使用相同功能条目链接。

```markdown
# Phase → Docs 功能追溯

## 功能主条目
| 父功能 | 具体子条目 | 名称 | 当前主说明 | 源码主归属 |
|---|---|---|---|---|
| FXX | {{稳定子锚点}} | {{名称}} | {{Docs 相对路径#准确锚点}} | {{主模块及协作}} |

## 逐阶段需求
| Phase / FR / TC | Docs 主条目及必要协作条目 | 状态 / 限制 |
|---|---|---|
| PNN FR-1 | {{功能锚点}} | {{现行 / 规划 / 冲突 / 历史}} |
```

**第三段：Docs ⇄ 代码**，由对应功能页的实现表维护。全局索引保存反查导航；当前完整函数、字段、状态和参数详情在主题页维护。Phase 仍保留本次完整设计映射。

本仓库的实际路径示例：

```text
SmartCar/specs/features/12-control-safety-closure/requirements.md：FR-2
  → SmartCar/Docs/system/runtime-and-safety.md#f02-stop
    → App/system/safety.c：Safety_RequestStop
    → App/control/motor.c：Motor_EmergencyStop
    → BSP/bsp_runtime.c：BSP_Runtime_StopTimers
```

该例仅展示定位，不表示首因冲突已经修复。从模块反查时，经 `Docs/architecture.md` 进入主功能，再查关联 Phase；不要求为了导航给每个源文件增加注释。

### 4.6 Docs 的全局入口

| 文件 | 保存内容 | 不重复保存的内容 |
|---|---|---|
| `index.md` | 读者入口、功能主题、当前重要限制 | 各功能的全部算法和接口 |
| `architecture.md` | 分层、依赖、状态归属概览、模块到主功能导航 | 各模块完整符号清单 |
| `traceability.md` | 稳定功能注册、Phase/FR/TC 到功能条目 | 第二套详细实现表 |
| `parameters.md` | 参数分类、适用模式、主说明及源码反查到具体参数表 | 与主题页重复维护数值 |
| `known-issues.md` | 问题 ID、现状、未决状态、所属功能/修复入口 | 与功能页独立演进的另一份契约 |
| `guides/` | 构建、烧录、验证工具、证据解释等公共方法 | 伪装成当前通过的历史结果 |

问题候选方案、决定和修复任务可放所属 Phase 或明确的专项台账；全局问题页只做状态及导航。关闭问题必须有实际依据，不能因为“文档已描述”就标已修复。

### 4.7 现状、目标与历史的处理

| 状态 | 写法 | 维护要求 |
|---|---|---|
| 当前已实现 | 写实际行为和代码定位 | 同时注明验证范围，不能推定实机通过 |
| 已批准待实现 | 目标草案留 Phase | 仅开工组 Docs 可标本组实现同步中、Phase/任务组与更新前代码基线；完成前核对一致 |
| 待决定 | 并列事实、要求、选项和影响 | 暂停依赖此决定的编码；无关工作可继续 |
| 规划 / 未接入 | 明确前置和边界 | 不作为当前对外能力 |
| 历史 / 已替代 | 写原基线、日期和替代入口 | 保留原编号、用户决定、提交及真实结果 |

迁移旧 Phase 时逐条核对 FR/TC、设计、映射、计划及验收，正文直接可读，不能藏进“失效历史”折叠区或替换成 Docs 跳转。旧路径按当时基线解释，必要时追加现行导航和带日期的勘误。

已有 JSON 迁移表、旧符号表、日志和摘要仍是历史定位工具；不为“看起来一致”重写原始证据。阶段协议保留完整快照、字段、测试向量和锚点；当前 Docs 另说明实际实现及与阶段快照的差异，不因恢复历史而修改协议。

## 6. 配套工作流（分支、提交与验证）

### 6.1 分支与提交顺序

```text
确认本次任务范围和现有改动，阅读治理 → Phase → Docs → 代码
  → 新 Phase 或进行中 Phase 新任务组完整保存设计、映射、验收及 Docs 目标草案
  → 记录用户决定，消除本批未决设计
  → Phase 确认并独立纯规约提交
  → 先更新开工组 Docs，标本组实现同步中、Phase/任务组及更新前代码基线
  → 紧接着修改本组代码 / 配置（后续组目标仍留 Phase）
  → 执行强制检查与本次选定验证
  → 双向核对 Docs 与代码，完成本组前取消同步标记
  → 匹配 Docs 与代码同批交付；Phase 记录真实结果并更新 roadmap / CHANGELOG
  → 提交前检查明确暂存清单；是否合并 / 推送按授权执行
```

1. **治理分支**：SmartCar 使用 `chore/constitution-<topic>` 处理 mission/techstack 治理修改、新阶段或重大重排，作纯文档提交。
2. **功能分支**：使用项目约定，例如 SmartCar 的 `feature/NN-<name>`；其他项目可以使用既有前缀，不机械覆盖工具和团队规则。
3. **再规划分支**：SmartCar 的大规模再规划使用 `chore/replan-<topic>`；技术红线变化仍核对治理影响。
4. **规约与实现分离**：后续小修、注释整改、机械重命名和工程配置修改同样先提交规约增量，不能把规约与其对应实现首次混在一起提交。
5. **纯文档任务**：只改资料、链接或整理契约时，不人为制造实现提交或新增 Phase；按本次任务文档范围提交。
6. **提交边界**：开始和提交前检查仓库状态。仅按明确路径暂存，检查暂存清单和差异；不用 `git add .`、`git add -A` 或 `git commit -a` 混入其他在途工作。
7. **提交与授权**：SmartCar 当前要求提交前展示文件清单、差异摘要和中文提交信息；范围核对通过后可按已有授权自动 commit，无须逐次请求许可，默认不 push。其他项目采用其明确规则。

### 6.2 验证选择与证据边界

本体系要求验证可判定、记录真实，不规定所有项目必须使用同一套脚本。SmartCar 当前按 2026-10-31 用户决定执行：

| 变更 / 检查类别 | 执行要求 | 记录与限制 |
|---|---|---|
| 格式、命名和注释内容 | 适用范围内强制审查 | 核对实际单位、调用、状态和错误路径，不以模板数量代替内容 |
| 上下文逻辑 | 强制审查 | 检查调用/写入顺序、接口、并发、时序和模块冲突 |
| 固件代码或工程配置改变 | 当前配置编译零错误、零警告 | 无法执行则记录未验证与原因，不填通过 |
| R08 实现提交复核 | 继续强制，按既有接口更新人工证据及真实依赖摘要 | 检查器通过不等于中文说明正确；纯文档不触发实现检查 |
| 双 LCD、架构/迁移、宿主行为及资源对照 | 按本次影响和验收目标选择 | 优先复用已有入口，不能静默跳过本任务已经明确约定的验证 |
| 纯文档变更 | 内容、路径、锚点、追溯和差异范围核对 | 不要求固件编译或软件行为回归 |
| 真实硬件验收 | 保留对应阶段的实体条件和待验项 | 软件替身、编译和宿主结果不能替代板上结论 |

尽可能减少直接测试软件实现的新增脚本、临时 C 驱动、模拟对端和其他脚手架；确有任务需要时先说明验收目的并复用已有工具。不因减少软件测试删除现有硬件测试能力，也不把历史全量检查自动恢复成每次开发的门禁。

其他项目应明确自己的强制项、按需项和纯文档范围；R08、双 LCD、AC5 等属于 SmartCar 的具体机制，不是所有采用 SDD 的项目都必须引入的工具。

### 6.3 结果状态与完成标准

结果至少区分：**通过、失败、未执行、阻塞、硬件待验、历史已通过**。写清日期、版本、环境、配置、对象与限制。

- 构建通过只能证明对应配置可构建，不证明实时性、波形、吞吐或控制效果。
- 宿主测试只证明刺激范围内的软件行为，不证明真实外设或完整分支覆盖。
- 某个独立子项通过，不等于被缺样本阻塞的完整入口通过。
- 预算、估算和历史值不能写成当前实测值；摘要对齐也不证明所有设计正确。
- 阶段复选框仅在约定验收全部完成后勾选；实现完成但硬件待验分别记录。

### 6.4 文档体系验收

交付前至少核对：

1. 每个功能 ID 有唯一主条目和稳定锚点；各模块有归属，第三方与生成区边界明确。
2. 每条有效 Phase FR/TC 能进入准确 Docs 条目，规划、历史及冲突状态有说明。
3. 每个已实现功能可定位真实代码、关键符号、状态 owner、调用上下文及验证方法；未实现功能不冒充现行能力。
4. Phase 与 traceability 的目标一致；模块能经 architecture 反查功能和关联需求。
5. Phase 完整保存本次算法、接口、格式、映射及验收；Docs 保存当前说明，按各自基线解释。协作 Docs 页引用主主题，不各维护冲突值表。
6. 参数默认/恢复/活动/镜像、配置矩阵及覆盖/生效/持久化完整可查；按父子主归属与旧入口走通准确主题。
7. 当前方法、实际执行结果、历史记录和硬件待验分开；原编号、决定和证据未被整理覆盖。
8. 相对链接、锚点及目录大小写正确；纯文档任务没有夹带源码、配置、其他报告或构建产物。
9. 检查方式与任务相称，不为了文档验收例行新增永久检查器或软件行为测试。

```text
任务：{{目标、技术约束或阶段顺序调整}}
先检查影响和已有用户决定，再按项目规则建立治理或再规划分支。
保留原 Phase 身份和历史记录，明确新增、取消或重排的原因。
同步受影响治理、Phase 与 Docs，先独立提交文档；本轮若仅授权
再规划，不修改代码或配置，不因更新技术栈就自动升级依赖。
```

### 7.6 独立文档迁移或修复

```text
仅重整文档：{{范围与输入报告}}
按前层治理文档 → Phase → Docs ⇄ 代码组织，可拆方案、任务组、决策台账及验收记录。
先写 Docs 现行契约并对照代码，再逐条整理 Phase 和治理入口。
保留原编号、完整阶段设计/映射/计划/验收、用户决定、历史证据及待验状态；冲突登记但不修行为。
保留七领域与 F 身份，落实父子主归属及旧锚点兼容，参数完整登记。
最后核对语义、配置矩阵、双向映射、需求索引、模块、链接、锚点和差异。
不新增开发阶段、固件行为或永久检查脚本，按任务组提交，不推送。
```

## 8. 常见反模式（Avoid）

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 口头要求编码，之后再补规约 | 目标和依据无法追溯 | Phase 完整设计确认独立提交，本组先 Docs 紧接代码并同批交付 |
| 只在 Phase 页首加 Docs 总链接 | 具体 FR 仍无法准确定位 | 逐条链接稳定功能锚点 |
| 为避免重复把 Phase 降成摘要或折叠历史 | 原设计依据丢失 | 完整保存阶段设计/映射/验收；Docs 保存当前实现，各按基线解释 |
| 每个 C/H 强制一篇 Markdown | 文档碎片化，辅助函数失去语义归属 | 按功能组织，模块反查主条目 |
| 需求不写细节，Docs 也省略实现定位 | 执行者被迫临场决定设计 | Docs 补齐关键符号、owner、状态和时序 |
| 把代码现状写成已经批准的行为 | 缺陷和兼容冲突被悄悄合法化 | 并列事实、要求、未决问题和修复入口 |
| 把整阶段目标预写入 Docs | 未开工能力冒充交付 | 草案留 Phase，仅开工组短暂标实现同步中，核对一致后取消标记 |
| 人工或智能体单改一份文档 | 索引、入口和阶段结果脱节 | 同步核对所有受影响引用 |
| 修改原日志、JSON 或旧基线以适配现状 | 历史证据失真 | 保留原证据，新增本轮结果并注明版本 |
| 编译/宿主通过就勾硬件验收 | 未验证风险被隐藏 | 分开记录工具链、样本、板上及实车结果 |
| 每次都恢复历史全量脚本门禁 | 验证与任务脱节，增加维护负担 | 执行现行强制项，按影响选择其余验证 |
| 因减少测试而跳过代码审查或适用构建 | 失去基础质量约束 | 保留格式、注释、逻辑及项目规定的构建/证据检查 |
| 为文档整理顺手修复行为或新增阶段 | 扩大授权范围、绕过决定 | 未决修复列台账，按所属 Phase 另行规约先行 |
| 批量暂存整个仓库或默认推送 | 混入其他在途工作或越过发布授权 | 明确路径暂存，检查差异，按授权提交/推送 |

## 9. 给智能体的最终指令（生成或维护骨架用）

> 将本节连同本规范交给智能体使用。已有体系应优先增量维护，不能看到模板就覆盖全部文档。

```text
请阅读 SDD 文档体系规范 2.0，为我的项目建立或完善文档体系。

项目描述：{{背景、目标、范围}}
现有材料：{{README、代码、阶段文档、报告或其他来源}}
本次授权范围：{{仅文档 / 规约准备 / 已授权实现的具体范围}}

要求：
1. 先核对工作区状态、仓库根和项目根，读取适用规则；
2. 保留已有身份、用户决定、历史结果和在途改动，不盲目重建；
3. 按第 2 节建立必要目录，使用大小写准确的 Docs/；
4. 按第 3 节完善治理文档，按第 4 节建立阶段三件套和功能契约；
5. 前层治理约束 Phase；Phase 完整保存背景、需求、详细设计、用户决定、
   计划、文件/符号映射、验证标准和结果；Docs ⇄ 代码表达当前功能、算法、
   参数、状态、时序、错误和兼容语义，不要求逐行翻译；
6. 每功能分配稳定 ID 和唯一主锚点；每条 FR/TC 经 traceability
   进入 Docs，再从功能页定位实现；模块可经 architecture 反查；
7. 未开工目标留 Phase；已结束阶段后的独立修改新增 Phase，进行中可增组；
   未知事实与行为冲突列具体选项，等待用户决定；
8. README、CHANGELOG、AGENTS、问题和研究入口按职责同步；
9. 验证按项目现行分类规则选择，纯文档不触发固件或行为回归，
   不为了验收例行新增永久检查器，不把硬件待验改成通过；
10. 交付文件清单、追溯和链接检查结果、未决/待验项；
11. 实现前先确认并独立提交 Phase 完整规约；每组先更新 Docs，标本组实现
    同步中、Phase/任务组及更新前代码基线，紧接代码；核对一致后取消标记，
    匹配 Docs 与代码同批交付，中断则保留实际同步状态；
12. 保留领域及 F 身份，父/子条目明确主说明，旧锚点保留准确导航；参数索引
    指向具体主表，数值/单位/默认/范围/覆盖/生效/持久化完整可查；
13. 提交、合并、推送遵守已有用户授权和项目规则。
```
