# SDD 文档体系规范 2.0（规约驱动开发文档体系）

> **本文档的用途**：这是一份自包含的规范，描述一套采用 **Phase → Docs → 代码** 关系的规约驱动开发（Spec-Driven Development）文档体系。
> 可以直接将本文档交给 AI 编程智能体，指令它：“阅读本文档，结合我的项目现状建立或维护文档体系。”第 7、9 节的提示词是可复制模板，不是阅读本文时自动执行的任务。
> **版本与依据**：2.0，2026-10-31。沿用《SDD文档体系规范》的九章编排，根据 STM32H7 仓库现有 SmartCar 文档体系整理；目录大小写以 `Docs/` 为准，编写时参考提交为 `7f48e08`。
> **适用边界**：本规范提炼通用方法，并在相关位置注明 SmartCar 的实际规则。它是文档体系说明，不自动改变项目已有授权、阶段排期或验收状态；项目具体执行规则由对应范围的 `AGENTS.md` 和现行治理文档维护。

## 1. 设计理念与原则

本体系源自规约驱动开发（SDD）方法论，核心思想是：**Phase 记录变更依据，Docs 维护功能契约，代码实现契约**。

```text
Phase：为什么做、做哪些、按什么顺序做、何时验收
                         ↓
Docs：功能、接口、状态、规则、实现位置与验证方法
                         ↓
代码：实现上述功能与契约
```

读者路径：**查开发任务看 Phase，理解当前功能看 Docs，检查实现看代码。**

### 1.1 八条核心原则

1. **规约先行**：新增、修复、重构、删除代码或修改工程配置前，先明确 Phase 需求和对应 Docs 目标契约，完成不含实现代码的独立规约提交，再开始实现。机械改名同样适用；只读调查与不修改仓库的构建取证可按项目规则直接进行。
2. **职责唯一**：Phase 保存动机、编号需求、用户决定、任务和实际验收；Docs 唯一维护现行功能详情及实现、验证定位。代码映射、算法和格式不在两层各维护一份。
3. **人在回路**：影响外部行为、接口、安全、兼容性、实时性、参数或休眠代码处置的未决事项必须由用户决定。已明确授权的常规编辑、核对和提交按项目规则推进，不对每个步骤重复索取许可。
4. **语义对应**：一个功能有一个稳定 ID 和唯一主说明条目；协作实现可以涉及多个文件，辅助函数归入所属功能，不机械要求每个 C/H 单独建立 Markdown。
5. **小步提交**：按可审查的任务组推进。规约提交先于实现，完成后及时回填事实、验证结果和阶段进度。
6. **同步维护**：无论人工还是智能体修改，都要核对相关 Phase、Docs、入口及索引。目录改名、移动或接口变化必须修复引用，避免文档漂移。
7. **事实与目标分开**：当前实现、已批准目标、待决定方案和历史结果分别标记。描述实现不代表批准其行为；源码存在不代表硬件通过，测试通过不代表所有风险已消除。
8. **工具无关**：正文采用 Markdown，不绑定某一智能体或问答工具。JSON、日志、图片和构建产物可以作为证据或辅助索引，但不替代可读功能契约。

### 1.2 文档角色与三级关系

“Phase → Docs → 代码”是变更到实现的追溯关系。项目治理和辅助资料分别提供执行约束与证据，不与功能契约争夺权威。

| 角色 | 内容 | 生命周期 | 唯一维护位置 |
|---|---|---|---|
| **项目治理** | 使命、技术约束、代码标准、路线图、协作步骤 | 长期维护 | `specs/mission.md`、`techstack.md`、`code-style.md`、`roadmap.md`、`AGENTS.md` 各司其职 |
| **阶段层（Phase）** | 动机、FR/TC、用户决定、任务/依赖/风险、阶段验收事实 | 分支结束后仍保留 | `specs/features/NN-<name>/` |
| **现行功能层（Docs）** | 功能契约、接口/格式、状态/时序、代码定位、验证方法及限制 | 跨阶段持续演进 | `Docs/` 的唯一功能主条目 |
| **辅助层** | README、变更日志、研究、专项报告和原始证据 | 按用途维护或冻结 | 对应入口、`specs/research/`、报告目录及证据文件 |

权威按问题划分：查“为什么改、谁决定、何时验收”看 Phase；查“当前功能如何工作、哪里实现、如何验证”看 Docs；查实际执行语句看代码。若三者冲突，登记冲突并确认目标，不能自动选择旧文档或当前代码作为新的设计决定。

### 1.3 相对原版的主要变化

| 原版安排 | 2.0 安排 |
|---|---|
| 功能三件套承载主要功能说明 | Phase 三件套定义变更，Docs 承接跨阶段维护的功能契约 |
| 功能规约与代码直接关联 | Phase/FR → Docs 条目 → 实现与验证，支持模块反查 |
| `specs/` 是主要阅读中心 | `specs/` 管治理和阶段，`Docs/` 是现行功能入口 |
| 需求不写内部实现细节 | Phase 不复制细节；Docs 必须写足文件、关键符号、状态归属与时序 |
| 每组默认运行自动化验证 | 强制审查与适用构建保留，其他验证按影响选择，纯文档只核对文档 |
| 每次提交都等待人工确认 | 未决设计必须确认，常规提交遵守已授权范围及仓库规则 |
| 规约主要随功能分支使用 | Phase 历史长期保留，Docs 持续反映现行契约 |

## 2. 目录结构

标准目录相对于**受本体系治理的项目根目录**，不必等于 Git 仓库根目录。

```text
<Git 仓库根目录>/
├── AGENTS.md                         # 仓库入口：目录范围和 Git 边界
├── <项目目录>/                       # 单项目仓库可直接使用仓库根目录
│   ├── AGENTS.md                     # 项目协作步骤、阅读顺序与执行规则
│   ├── README.md                     # 简介、当前状态、构建和文档入口
│   ├── CHANGELOG.md                  # 已发生的变更，不代替阶段进度
│   ├── specs/
│   │   ├── mission.md                # 为什么做、范围及治理原则
│   │   ├── techstack.md              # 技术选型、版本和硬性约束
│   │   ├── roadmap.md                # 阶段顺序、当前状态和排期
│   │   ├── code-style.md             # 代码格式、命名和注释标准
│   │   ├── features/
│   │   │   └── NN-<kebab-case-name>/
│   │   │       ├── plan.md           # 任务组、顺序、依赖、风险和回退
│   │   │       ├── requirements.md   # FR/TC、动机、决定及 Docs 条目引用
│   │   │       └── validation.md     # 阶段标准、执行记录和证据入口
│   │   └── research/
│   │       └── YYYY-MM-DD-<topic>.md
│   ├── Docs/
│   │   ├── index.md                  # 功能阅读入口
│   │   ├── architecture.md           # 架构、模块归属和反向导航
│   │   ├── traceability.md           # Phase/FR/TC → Docs 唯一索引
│   │   ├── known-issues.md           # 当前问题、冲突和未决事项入口
│   │   ├── <domain>/
│   │   │   └── <functional-topic>.md # 现行功能契约与实现/验证映射
│   │   └── guides/
│   │       ├── build-and-flash.md    # 构建/部署/烧录方法，按项目命名
│   │       └── validation.md         # 验证方法、工具与证据边界
│   └── ...                           # 产品代码、工程、已有测试与证据
├── Reports/                          # 可选：独立审计、迁移方案和专题交付
└── ...                               # 硬件、材料、工具和其他独立项目
```

### 2.1 命名规则

- 阶段目录为 `NN-<kebab-case-name>`，NN 与 roadmap 的阶段身份对应；阶段增多时可扩展位数，但不得借排序改掉已有编号。
- 功能 ID 独立于 Phase 编号。示例：`F02` 是起停功能，`P12 FR-2` 是某次阶段需求，二者不是一对一关系。
- 主条目使用显式稳定锚点，如 `<a id="f02"></a>`；必要时细分 `f02-start`、`f02-stop`。标题改写不应改变这些锚点。
- 可按维护领域增加阶段分组，但分组不是新身份。调整路径必须同步相对链接、索引和入口，并记录迁移。
- `Docs/` 的 D 必须大写。其内部文件和领域目录通常使用小写英文加连字符；`AGENTS.md`、`README.md`、`CHANGELOG.md` 保留固定名称。
- 研究记录使用 `YYYY-MM-DD-<topic>.md`。既有中文资料名和用户指定交付名可以保留，不为“统一命名”擅自重命名历史资料。
- 仓库内链接优先使用相对路径和稳定锚点；聊天交付链接可使用文件绝对路径。代码行号只作辅助，关键定位使用真实文件和符号。

## 3. 项目层：宪章与治理（Constitution）

治理文档定义项目目标、技术红线和协作方式，不复制全部功能正文。治理原则或重大排期变更走项目规定的独立分支与纯文档提交；日常进度回填可随对应功能提交。

### 3.1 `specs/mission.md` —— 使命

**回答“为什么做、边界在哪里、如何治理”**。模板：

```markdown
# 使命（Mission）

## 愿景
{{项目存在的意义}}

## 目标用户 / 受众
{{谁使用、维护或评审项目}}

## 范围
### 范围内（In Scope）
- {{明确交付}}
### 范围外（Out of Scope）
- {{明确排除；多项目仓库写清目录边界}}

## 语气与风格
{{语言、术语和可判定表述要求}}

## 成功标准
{{宏观且可核对的成功条件}}

## 项目治理原则
- Phase → Docs → 代码，目标契约独立提交先于实现。
- 未决设计由用户明确决定，不能以当前代码自动批准行为。
- 当前事实、待实现目标、历史验收及待验事项分开记录。
- 详细契约在 Docs 唯一维护；阶段保留变更依据与实际结果。
```

**编写要点**：目标受众和范围必须明确；不要把一个子项目的规约门禁推广到整个仓库，也不要让范围边界阻止其他目录已获授权的工作。

### 3.2 `specs/techstack.md` —— 技术栈

**回答“用什么做、有哪些不可越过的约束”**。模板：

```markdown
# 技术栈（Tech Stack）

## 语言与运行时
- {{语言、版本、运行环境}}

## 框架与核心库
| 类别 | 选型 | 版本 / 来源 | 理由 |
|---|---|---|---|
| {{类别}} | {{名称}} | {{实际版本或提交}} | {{理由}} |

## 数据存储
- {{介质、容量和责任边界；格式详情链接 Docs}}

## 构建与工具链
- {{编译器、构建系统、依赖和版本限制}}

## 验证政策
- {{强制审查、适用构建、按需验证及硬件验收边界}}
- {{详细执行规则链接 AGENTS；工具方法链接 Docs}}

## 硬性约束
- {{分层、周期、并发、内存、协议兼容和版本红线}}

## 当前功能导航
- {{Docs 入口、架构及相关功能条目}}
```

**编写要点**：版本从依赖和工程事实提取，不能猜测；选型变化先明确影响。硬约束在此维护，算法、字段表和调用链转到 Docs。

### 3.3 `specs/roadmap.md` —— 路线图

**回答“按什么顺序做、现在做到哪里”**。模板：

```markdown
# 路线图（Roadmap）

## 阶段总览
### Phase NN: {{阶段名}} `NN-<name>`
- [ ] {{全部约定验收完成才勾选}}
- 规模：{{nano / small / medium}}
- 阶段规约：{{三件套路径}}
- 受影响功能：{{稳定功能 ID；具体追溯见 Docs/traceability.md}}
- 依赖：{{前置阶段或用户决定}}

## 当前状态
- 已完成：{{可证实结果}}
- 实现完成但待验：{{构建、硬件或外部依赖}}
- 进行中：{{当前工作}}
- 下一步：{{顺序及理由}}

## 决策与排期变化
- {{日期、决定、原因、受影响阶段}}
```

**编写要点**：区分软件完成与全部阶段验收完成；不因整理文档补勾硬件项，不为一次文档迁移自动新建阶段。编号保持稳定，重大重排留下原决定。

### 3.4 `specs/code-style.md` —— 写作标准

定义代码格式、命名、注释、固定接口名及生成区/第三方例外。标准是长期约束；某次历史迁移授权不是以后实现的永久禁令。

模板至少包含：适用文件范围、格式与命名、接口与注释要求、例外、行为保持边界、审查清单和版本记录。功能算法归 Docs，协作执行归 AGENTS，不在多份文档复制完整标准。

SmartCar 已采用“C 完整、H 摘要”和 R08 人工证据机制，2.0 不另外复制 CS 条款或 JSON 结构；具体标准和记录接口继续由现有权威文件维护。

## 4. 阶段层与现行功能层：Phase → Docs

每个阶段保留 `plan.md`、`requirements.md`、`validation.md` 三件套。**实现前的规约提交同时包含受影响 Phase 与对应 Docs 目标契约**，不只提交三份空骨架或总链接。

### 4.1 `plan.md` —— 实现计划

```markdown
# Phase NN: {{阶段名}} — 实现计划

## 目标
{{本次交付及范围；不重复完整功能设计}}

## 背景与依据
- 关联治理：{{相关条款}}
- 前置条件：{{依赖、基线与已经确认的用户决定}}

## 任务分组（Task Groups）
### Group 1: {{组名}}
- [ ] {{任务与交付物}}
- 契约入口：{{Docs 文件及准确功能锚点}}
- 完成标准：{{可判定结果，关联 FR / V}}

### Group 2: {{组名}}
- [ ] {{任务与交付物}}
- 契约入口：{{Docs 功能锚点}}
- 完成标准：{{可判定结果}}

## 顺序与依赖
{{组间顺序、先行规约提交及外部前置}}

## 风险、取舍与回退
{{已确认取舍、回退单位、触发条件；详细状态/接口链接 Docs}}

## 未决事项
{{具体问题、候选方案、影响与负责人；无未决时明确说明}}
```

**编写要点**：任务组是自然提交单位。详细文件/符号、数据布局和设计通过 Docs 定位；不能只写“按需调整”或让执行者临场决定外部行为。

### 4.2 `requirements.md` —— 需求与用户决定

```markdown
# Phase NN: {{阶段名}} — 需求

## 变更动机与范围
{{为什么改、现状证据、交付边界}}

## 功能需求
<a id="fr-01"></a>
### FR-1 {{需求名}}
- 要求：{{可观测的目标及边界}}
- 权威功能条目：{{Docs 相对链接及稳定锚点}}
- 状态：{{规划 / 待决定 / 待实现 / 已实现待验 / 已验收}}

## 技术约束
### TC-1 {{约束名}}
- 约束：{{可判定要求}}
- 关联条目：{{Docs 功能锚点或治理条款，并给功能入口}}

## 用户决定
| 日期 | 问题 | 明确决定及理由 | 影响 FR / Docs |
|---|---|---|---|
| {{日期}} | {{问题}} | {{用户已确认的内容}} | {{编号 / 条目}} |

## 非目标（Non-goals）
- {{本次明确不做的工作}}
```

**编写要点**：Phase 保留“要什么”和决定依据，每条有效 FR/TC 指向具体 Docs 条目。协议、格式和接口详情链接到 Docs；关键符号必须在 Docs 明确，不能用“不微操实现”为由遗漏。

同一功能可被多阶段改变；同一需求可关联多个协作功能，但必须确定主条目。已发布 FR/TC 编号不因重排、拆页或目录迁移改号。

### 4.3 `validation.md` —— 阶段验收与执行事实

```markdown
# Phase NN: {{阶段名}} — 验证

## 本次验证范围
- 基线 / 被验证提交：{{可定位版本}}
- 本次强制项：{{依据及选择}}
- 按需项：{{选择或未选择的理由}}
- 前置与待验：{{硬件、样本、许可或外部环境}}

## 验证清单（Scorecard）
| ID | 检查项 | 方法入口 | 本阶段通过标准 | 关联需求 |
|---|---|---|---|---|
| V-1 | {{对象}} | {{Docs 功能条目 / 验证章节}} | {{可观测判据}} | FR-1 |

## 实际执行记录
| 日期 / 提交 | 验证项 | 环境 / 配置 | 实际结果 | 证据 / 限制 |
|---|---|---|---|---|
| {{实际填写}} | V-1 | {{实际环境}} | {{通过 / 失败 / 阻塞 / 未执行}} | {{日志 / 人工观察 / 原因}} |

## 剩余项目与结论
```

### 4.6 Docs 的全局入口

| 文件 | 保存内容 | 不重复保存的内容 |
|---|---|---|
| `index.md` | 读者入口、功能主题、当前重要限制 | 各功能的全部算法和接口 |
| `architecture.md` | 分层、依赖、状态归属概览、模块到主功能导航 | 各模块完整符号清单 |
| `traceability.md` | 稳定功能注册、Phase/FR/TC 到功能条目 | 第二套详细实现表 |
| `known-issues.md` | 问题 ID、现状、未决状态、所属功能/修复入口 | 与功能页独立演进的另一份契约 |
| `guides/` | 构建、烧录、验证工具、证据解释等公共方法 | 伪装成当前通过的历史结果 |

问题候选方案、决定和修复任务可放所属 Phase 或明确的专项台账；全局问题页只做状态及导航。关闭问题必须有实际依据，不能因为“文档已描述”就标已修复。

### 4.7 现状、目标与历史的处理

| 状态 | 写法 | 维护要求 |
|---|---|---|
| 当前已实现 | 写实际行为和代码定位 | 同时注明验证范围，不能推定实机通过 |
| 已批准待实现 | 显式标“待实现目标”并写批准依据 | 保留当前行为直到实现完成，不能提前改成现状 |
| 待决定 | 并列事实、要求、选项和影响 | 暂停依赖此决定的编码；无关工作可继续 |
| 规划 / 未接入 | 明确前置和边界 | 不作为当前对外能力 |
| 历史 / 已替代 | 写原基线、日期和替代入口 | 保留原编号、用户决定、提交及真实结果 |

迁移旧 Phase 时逐条处理 FR/TC、计划与验收，不只在页首增加 Docs 总链接。已承接的算法、格式、符号映射改成准确引用；必要历史正文可放明确的冻结区或折叠区，不继续作为现行契约维护。

已有 JSON 迁移表、旧符号表、日志和摘要仍是历史定位工具；不为“看起来一致”重写原始证据。旧协议文件可保留入口及章节锚点，正文迁入 Docs 后明确新的权威章节。

## 6. 配套工作流（分支、提交与验证）

### 6.1 分支与提交顺序

```text
确认本次任务范围和现有改动
  → Phase 定义变更与受影响功能
  → Docs 明确目标契约，记录用户决定，消除本批未决设计
  → 独立纯规约提交（Phase + 对应 Docs）
  → 按任务组修改代码 / 配置
  → 执行强制检查与本次选定验证
  → Docs 回填实现事实和验证状态
  → Phase 记录实际结果，更新必要的 roadmap / CHANGELOG
  → 检查明确暂存清单后提交；是否合并 / 推送按授权执行
```

1. **治理分支**：SmartCar 使用 `chore/constitution-<topic>` 处理 mission/techstack 治理修改、新阶段或重大重排，作纯文档提交。
2. **功能分支**：使用项目约定，例如 SmartCar 的 `feature/NN-<name>`；其他项目可以使用既有前缀，不机械覆盖工具和团队规则。
3. **再规划分支**：SmartCar 的大规模再规划使用 `chore/replan-<topic>`；技术红线变化仍核对治理影响。
4. **规约与实现分离**：后续小修、注释整改、机械重命名和工程配置修改同样先提交规约增量，不能把规约与其对应实现首次混在一起提交。
5. **纯文档任务**：只改资料、链接或整理契约时，不人为制造实现提交或新增 Phase；按本次任务文档范围提交。
6. **提交边界**：开始和提交前检查仓库状态。仅按明确路径暂存，检查暂存清单和差异；不用 `git add .`、`git add -A` 或 `git commit -a` 混入其他在途工作。
7. **提交与授权**：SmartCar 当前要求提交前展示文件清单、差异摘要和中文提交信息；范围核对通过后可按已有授权自动 commit，无须逐次请求许可，默认不 push。其他项目采用其明确规则。

### 6.2 验证选择与证据边界

本体系要求验证可判定、记录真实，不规定所有项目必须使用同一套脚本。SmartCar 当前按 2026-10-31 用户决定执行：

| 变更 / 检查类别 | 执行要求 | 记录与限制 |
|---|---|---|
| 格式、命名和注释内容 | 适用范围内强制审查 | 核对实际单位、调用、状态和错误路径，不以模板数量代替内容 |
| 上下文逻辑 | 强制审查 | 检查调用/写入顺序、接口、并发、时序和模块冲突 |
| 固件代码或工程配置改变 | 当前配置编译零错误、零警告 | 无法执行则记录未验证与原因，不填通过 |
| R08 实现提交复核 | 继续强制，按既有接口更新人工证据及真实依赖摘要 | 检查器通过不等于中文说明正确；纯文档不触发实现检查 |
| 双 LCD、架构/迁移、宿主行为及资源对照 | 按本次影响和验收目标选择 | 优先复用已有入口，不能静默跳过本任务已经明确约定的验证 |
| 纯文档变更 | 内容、路径、锚点、追溯和差异范围核对 | 不要求固件编译或软件行为回归 |
| 真实硬件验收 | 保留对应阶段的实体条件和待验项 | 软件替身、编译和宿主结果不能替代板上结论 |

尽可能减少直接测试软件实现的新增脚本、临时 C 驱动、模拟对端和其他脚手架；确有任务需要时先说明验收目的并复用已有工具。不因减少软件测试删除现有硬件测试能力，也不把历史全量检查自动恢复成每次开发的门禁。

其他项目应明确自己的强制项、按需项和纯文档范围；R08、双 LCD、AC5 等属于 SmartCar 的具体机制，不是所有采用 SDD 的项目都必须引入的工具。

### 6.3 结果状态与完成标准

结果至少区分：**通过、失败、未执行、阻塞、硬件待验、历史已通过**。写清日期、版本、环境、配置、对象与限制。

- 构建通过只能证明对应配置可构建，不证明实时性、波形、吞吐或控制效果。
- 宿主测试只证明刺激范围内的软件行为，不证明真实外设或完整分支覆盖。
- 某个独立子项通过，不等于被缺样本阻塞的完整入口通过。
- 预算、估算和历史值不能写成当前实测值；摘要对齐也不证明所有设计正确。
- 阶段复选框仅在约定验收全部完成后勾选；实现完成但硬件待验分别记录。

### 6.4 文档体系验收

交付前至少核对：

1. 每个功能 ID 有唯一主条目和稳定锚点；各模块有归属，第三方与生成区边界明确。
2. 每条有效 Phase FR/TC 能进入准确 Docs 条目，规划、历史及冲突状态有说明。
3. 每个已实现功能可定位真实代码、关键符号、状态 owner、调用上下文及验证方法；未实现功能不冒充现行能力。
4. Phase 与 traceability 的目标一致；模块能经 architecture 反查功能和关联需求。
5. 算法、接口、格式和完整实现表只在所属权威位置维护，协作页面使用链接。
6. 当前方法、实际执行结果、历史记录和硬件待验分开；原编号、决定和证据未被整理覆盖。
7. 相对链接、锚点及目录大小写正确；纯文档任务没有夹带源码、配置、其他报告或构建产物。
8. 检查方式与任务相称，不为了文档验收例行新增永久检查器或软件行为测试。

```text
实现 {{Phase / 任务组}}，以已经确认并独立提交的 Docs 目标契约为准。
1. 核对规约提交和当前状态，不混入已有改动；
2. 按任务组修改实现，遵守代码标准和状态/接口/并发约束；
3. 遇到新的行为歧义，停止该决定点相关编码，先回填并询问；
4. 执行强制检查和本轮选定验证，不默认新建测试脚手架；
5. Docs 回填实际实现和验证状态，Phase 记录结果与待验项；
6. 展示明确暂存范围、差异摘要和提交信息，按项目授权提交；
7. 未获明确要求不合并或推送，不把待验改成通过。
```

### 7.5 再规划与治理变更

```text
任务：{{目标、技术约束或阶段顺序调整}}
先检查影响和已有用户决定，再按项目规则建立治理或再规划分支。
保留原 Phase 身份和历史记录，明确新增、取消或重排的原因。
同步受影响治理、Phase 与 Docs，先独立提交文档；本轮若仅授权
再规划，不修改代码或配置，不因更新技术栈就自动升级依赖。
```

### 7.6 独立文档迁移或修复

```text
仅重整文档：{{范围与输入报告}}
按 Phase → Docs → 代码组织，可拆独立方案、任务组、决策台账及验收记录。
先写 Docs 现行契约并对照代码，再逐条整理 Phase 和治理入口。
保留原编号、用户决定、历史证据和待验状态；冲突登记但不修行为。
最后核对唯一主条目、需求索引、模块归属、符号、链接、锚点和差异。
不新增开发阶段、固件行为或永久检查脚本，按任务组提交，不推送。
```

## 8. 常见反模式（Avoid）

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 口头要求编码，之后再补规约 | 目标和依据无法追溯 | Phase 与 Docs 目标契约先行独立提交 |
| 只在 Phase 页首加 Docs 总链接 | 具体 FR 仍无法准确定位 | 逐条链接稳定功能锚点 |
| Phase 和 Docs 各存一套接口/算法/符号表 | 后续维护互相漂移 | Phase 引用 Docs，功能主页唯一维护详情 |
| 每个 C/H 强制一篇 Markdown | 文档碎片化，辅助函数失去语义归属 | 按功能组织，模块反查主条目 |
| 需求不写细节，Docs 也省略实现定位 | 执行者被迫临场决定设计 | Docs 补齐关键符号、owner、状态和时序 |
| 把代码现状写成已经批准的行为 | 缺陷和兼容冲突被悄悄合法化 | 并列事实、要求、未决问题和修复入口 |
| 编码前把目标写成当前能力 | 读者误以为功能已经交付 | 明确待实现，完成后再回填事实 |
| 人工或智能体单改一份文档 | 索引、入口和阶段结果脱节 | 同步核对所有受影响引用 |
| 修改原日志、JSON 或旧基线以适配现状 | 历史证据失真 | 保留原证据，新增本轮结果并注明版本 |
| 编译/宿主通过就勾硬件验收 | 未验证风险被隐藏 | 分开记录工具链、样本、板上及实车结果 |
| 每次都恢复历史全量脚本门禁 | 验证与任务脱节，增加维护负担 | 执行现行强制项，按影响选择其余验证 |
| 因减少测试而跳过代码审查或适用构建 | 失去基础质量约束 | 保留格式、注释、逻辑及项目规定的构建/证据检查 |
| 为文档整理顺手修复行为或新增阶段 | 扩大授权范围、绕过决定 | 未决修复列台账，按所属 Phase 另行规约先行 |
| 批量暂存整个仓库或默认推送 | 混入其他在途工作或越过发布授权 | 明确路径暂存，检查差异，按授权提交/推送 |

## 9. 给智能体的最终指令（生成或维护骨架用）

> 将本节连同本规范交给智能体使用。已有体系应优先增量维护，不能看到模板就覆盖全部文档。

```text
请阅读 SDD 文档体系规范 2.0，为我的项目建立或完善文档体系。

项目描述：{{背景、目标、范围}}
现有材料：{{README、代码、阶段文档、报告或其他来源}}
本次授权范围：{{仅文档 / 规约准备 / 已授权实现的具体范围}}

要求：
1. 先核对工作区状态、仓库根和项目根，读取适用规则；
2. 保留已有身份、用户决定、历史结果和在途改动，不盲目重建；
3. 按第 2 节建立必要目录，使用大小写准确的 Docs/；
4. 按第 3 节完善治理文档，按第 4 节建立阶段三件套和功能契约；
5. Phase 保存需求、动机、决定、任务和验收，Docs 唯一维护当前
   功能/接口/状态/实现映射/验证方法，代码是契约的实现；
6. 每功能分配稳定 ID 和唯一主锚点；每条 FR/TC 经 traceability
   进入 Docs，再从功能页定位实现；模块可经 architecture 反查；
7. 新功能标待实现；未知事实和行为冲突列具体选项，等待用户决定；
8. README、CHANGELOG、AGENTS、问题和研究入口按职责同步；
9. 验证按项目现行分类规则选择，纯文档不触发固件或行为回归，
   不为了验收例行新增永久检查器，不把硬件待验改成通过；
10. 交付文件清单、追溯和链接检查结果、未决/待验项；
11. 任何实现前，先完成 Phase 与 Docs 目标契约的独立纯规约提交；
    提交、合并、推送遵守已有用户授权和项目规则。
```
