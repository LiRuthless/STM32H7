## 代码设计原则：适度模块化

2026-11-07用户长期决定，适用于本工程自维护代码的设计、编写、修改及审查；本节是原则的唯一维护正文，其他治理文档与Docs通过链接引用。

1. 遵循项目现有的架构和模块边界。
2. 按业务职责、复杂逻辑、依赖边界组织代码。
3. 函数应具有明确的语义、复用价值，或者能够隔离复杂性和副作用。
4. 不要仅为了缩短代码而拆分函数。
5. 避免无意义的包装函数、参数透传函数、空洞抽象层和过深的调用链。
6. 允许只调用一次的函数存在，前提是它确实改善了代码的可维护性。
7. 不要为假设中的未来需求提前设计架构。
8. 优先复用现有实现，不随意新增设计模式。
9. 不进行与当前任务无关的重构。
10. 完成后检查不必要的抽象，但不得为了减少代码量损害可读性、正确性、可测试性和必要的模块化。

**核心目标：最小的合理复杂度，而不是最少的代码行数。**

### 本工程审查与实施要求

- 短函数、单调用函数、getter、回调适配和薄入口不按行数或调用次数判定好坏；核对其业务语义、状态封装、SDK签名、任务/依赖边界和副作用隔离的实际价值。下文允许单调用转发省略details只是注释规则，不是设计合理性的证明。
- 审查应给出具体文件/符号、调用方与状态owner、发现及影响，并分别记录保留理由、可实施修改和未决事项；不为压低函数数、文件数或调用层数机械合并。没有必要修改的模块可以保留并说明理由。
- 重构设计在所属Phase记录调整前后职责、接口/调用关系、受影响符号、保持不变的行为和验证标准；交付复核新增及保留抽象是否必要。不得用本原则绕过规约独立提交、Docs同步或未决行为确认。
- 可测试性是设计质量要求，不构成创建或运行软件测试的授权；继续执行AGENTS的真实链路验证政策及ESP-IDF v6.0.0构建要求。
- 本次只发布设计原则，不批准删除现有接口、变更生产行为、解除既有未决门禁或启动Phase06，不声明存量代码已全部符合。

## 2. 排版

- 4个ASCII空格，无Tab。函数、控制语句、结构体、枚举、多行初始化的大括号独占一行，else独占一行。if/else/for/while/do体含单条提前return也必须有大括号；空体展开并说明原因。
- case/default相对switch缩进一级，语句再一级；预处理#位于行首，续行用空格。
- 一行一条可执行语句，一条声明一个对象/字段。for头分号和可读标量数组不算例外违规；不为排版改变易变对象写入或求值顺序。
- 写作if (condition)、函数调用name(argument)。二元/赋值两侧各一空格，逗号后空格；一元运算、成员访问和下标不插空格。指针写const type_t *name，转换写(int16_t)value，sizeof带括号。
- 每行最多100字符，先在参数/运算符处换行，续行多一级缩进，运算符位于续行开头。不可拆分的协议/日志字符串、URL、哈希和版权原文可超长，不能将普通声明/注释据此豁免。
- 函数之间空一行，函数内按处理阶段分段；无行尾空白，文件末尾保留一个换行。新C/H用UTF-8无BOM，修改时保持原换行，避免无关全文件转换。

## 3. 命名与文件组织

- 文件名lower_snake_case。公开函数和自有类型沿用bridge_或scb_所属模块前缀，函数/变量lower_snake_case，类型以_t结尾；不迁入STM32的Module_ActionObject。
- 私有static函数使用职责明确的lower_snake_case，不因补前缀而全量改名。静态对象采用既有s_约定；自有可写状态优先私有，确需外部对象须带模块前缀，不为了命名改变static/extern/const/volatile、作用域或初始化时点。
- 自有宏/枚举项沿用BRIDGE_或SCB_的UPPER_SNAKE_CASE。新普通头文件保护宏采用BRIDGE_<文件主名>_H或协议模块既有SCB_约定，保证唯一；存量唯一保护宏及#pragma once不借本轮强迁移。
- 文件按说明、包含、私有宏/类型、对象、私有声明、实现组织；头文件按依赖、公开类型/常量、接口分组。不因排版重排有副作用的包含或初始化。
- app_main、SDK函数/类型/字段、注册接口要求的签名、IRAM_ATTR、段名、Kconfig/CMake变量、线字段/枚举数值均按真实外部约束保持。自有函数指针回调不是自动命名豁免。

## 4. 注释格式与权威位置

- 自维护C/H用Doxygen文件块，依次含@file、中文@brief、@details。C说明职责边界、输入→处理→输出、主要调用、状态owner和任务/ISR模型；H说明接口范围和实现模块。配置头只写配置职责，不虚构数据流。
- 采用“C完整、H摘要”：公开、私有、固定名回调及条件编译各分支的完整函数说明放在C定义前；H只用@brief/@note说明用途、调用者约束和实际C文件::函数名定位，不复制完整参数/算法表。
- 函数标签按@brief、@details、@param、@return、@pre、@note顺序；有参数按签名顺序逐项写@param[in]/[out]/[in,out]，非void返回写真实成功及错误语义。无参数、void返回、无额外前置条件时省略对应项，不填“无”“同上”。不用无方向@param或@retval替代本约定。
- 有计算、循环、状态转换、并发或错误路径须写details；纯getter/单调用转发可省略，并在本批审查注明类别。指针说明空值条件、借用期、输出提交时机及失败时是否保留；无显式形参的共享输入同样说明。
- 多行块首尾独占一行，正文以“ * ”开始，标签后一个空格，续行正文使用四空格续进，整块跟随代码缩进。注释紧邻所说明定义/代码块，无空行隔开。短阶段块可写单行/* 完整说明。 */。
- 自有结构体/枚举成员使用紧随的Doxygen尾注，声明与注释间一空格；长说明移到字段前的brief块。说明真实含义、单位、边界/哨兵和并发归属；状态对象定义前用块注说明读写上下文。
- 复杂实现按连续阶段说明目标、顺序原因、失败副作用及恢复，不逐句翻译赋值，自有说明统一块注，不混用//；不堆装饰分隔线、旧“函数名/功能/参数”模板或零散行尾注释。来源/版权原文单独保留，属于注释符号与行宽例外。


### 格式示例（文档示例，不修改接口）

以下只展示现有bridge_password_validate的C完整说明格式；实际定义前使用块注，H只保留brief和必要note。

~~~c
/**
 * @brief 检查本地热点密码字节是否合法。
 * @details 按显式长度校验，不打印或保存输入；非法值由启动层阻止AP启动。
 * @param[in] data 密码字节，不能为空，不能包含NUL或非ASCII字节。
 * @param[in] length 字节数，合法范围为8至63。
 * @return 合法返回ESP_OK，否则返回ESP_ERR_INVALID_ARG。
 * @note 由启动检查调用；不创建网络服务，不改变SPI状态。
 */
~~~

## 5. ESP32内容要求与行为边界

说明必须与实际调用者和实现核对，尤其包括：
- SPI/NET各自任务owner、Core/优先级、ISR边界、短临界区及锁顺序；
- DMA提交/回收证据、借用视图生命周期、固定槽释放及失败后保留；
- socket部分收发、有界等待、计时起点、可靠ACK与业务结果的区别；
- 计数是包/记录/事务还是字节，构建容量与实测堆栈的区别。

不编造硬件事实、阈值来源、性能或通过结论；缺事实登记问题。格式、注释和命名修改不得改变类型/布局、表达式及短路顺序、初始化、状态机、临界区、中断优先级、协议或日志格式。需改行为时先回所属Phase与Docs明确目标并独立提交规约。

## 2026-11-07 现行文档体系
