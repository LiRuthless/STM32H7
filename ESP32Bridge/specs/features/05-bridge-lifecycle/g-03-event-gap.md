# G-03：桥接端缺口报告的设备字段来源

2026-10-18用户明确选择“采用推荐的首个缺失源事件锚点方案”。先独立纯规约提交，再实施；不代表三端已兼容。

## requirements

05/FR-4：桥接端EVENT_GAP只标记确知无法交付的历史。event为`EVENT_GAP`；run_id、tick、control_sequence、revision全部原样取本轮缺口中第一条已验证、未能向电脑交付的STM32 EVENT，表示缺口锚点，不表示末端时刻或事件总数。不增加字段，不以ESP32时钟、0或猜值填充设备时序。

队满且未ACK的可靠帧仍可重试，不算确知丢失，不据此生成EVENT_GAP。没有可信源锚点时，只请求关闭TCP、重连后查询，不生成带猜值的EVENT_GAP。换SPI会话后不能把旧session锚点改标为新session；清理旧锚点，重连查询当前状态。

## plan

固定保存源锚点及待报告标记，只从完整协议/JSON验证后的源EVENT提取设备字段。已接管队列项保有归属，不因拥堵先ACK后丢。网络所有者执行无锚点关闭，SPI不调用socket。EVENT_GAP不等于完整历史或车辆状态恢复。

## validation

05/V-4、06/V-5：注入字段各异的缺失源EVENT，核对报告恰用首个锚点；重复可靠帧不重复入队/报告。验证队满未ACK不报缺口、无锚点关闭、换会话不重标旧锚点。方案已确认，代码/测试尚未完成。
